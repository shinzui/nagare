# Nagare 0.7.1

Nagare 0.7.1 fixes four deferred findings: upgrades and context changes work through the operator
symlinks of [ADR 13](../adr/0013-operator-deployment-material-lives-in-a-private-repository-with-remote-state.md),
and app databases' backups are suspended at retirement, graded and pruned.

## Fixed

- **The kubeconfig stage accepts an operator-linked kubeconfig (F127).** A context kubeconfig that
  is a symbolic link, such as an agenix secret, is read through the link. When its bytes match the
  accepted digest the stage writes nothing; when they differ, or the link is dangling, it refuses
  and names the link's target, since Nagare never writes through a link. A transition no longer
  needs a regular-file copy in its place.
- **Context control works through a symlinked context (F126).** `context apply` and
  `context restore` read a linked context file and its `.reviews` directory through their links
  and rename over the target, so the link survives. A dangling link refuses, and a linked
  context is removed in its private repository, not by context control.
- **Retiring an app database suspends its schedule (F131).** `db app-database retire` sets
  `spec.suspend` on `nagare-appdb-<name>` in the same review, and re-planning the declaration
  resumes it. The schedule revision is unchanged, so earlier runs still ingest and restore.

## Added

- **App databases' backups are graded and pruned (F132).** `server status` and `doctor` show a
  `recovery point` and a `retention` row labelled `<namespace>/<name>` for every app database; a
  retired one reads `retired; schedule suspended`.
  `nagarectl db app-database prune-scheduled-backups NAME --save-plan DIR` reviews the removal of
  runs past the retention policy, and `db app-database recover-scheduled-prune` finishes an
  abandoned partial prune, exactly as the database commands do. See
  [Sharing one server between apps](../user/managed-databases.md#sharing-one-server-between-apps).

## Install

```bash
export NAGARE_VERSION=0.7.1
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

## Upgrading

Move a context on 0.7.0 to 0.7.1 with the 0.7.1 `nagarectl`, as described in
[0.6.0's upgrade steps](v0.6.0.md#upgrading). A context kubeconfig that is a symbolic link stays
in place. An app database retired on 0.7.0 keeps its running schedule until it is retired again
with 0.7.1, which suspends it.

## Compatibility and rollback

`transitionsFrom` adds 0.7.0. Everything else is unchanged from 0.7.0.

## Known limitations

- Dropping a retired app database is not offered.
- A workload binds at most one database per engine across `databases` and `appDatabases`.
- Moving an existing direct consumer onto an app database is a data migration, not a rebinding.

## Validation

A green full gate and mutation sweep on the candidate, the native output and clone-free rehearsal
of each supported system, the EP-172 rehearsal record moving a seeded local context from 0.7.0 to
this release, `just local-app-database-smoke` on that context, and the work intranet upgraded on
the candidate, with its kubeconfig still a symbolic link, before the tag.
