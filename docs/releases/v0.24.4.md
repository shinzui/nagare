# Nagare 0.24.4

A cloud delegated deployer can publish images to its delegation's own repository and deploy sites into its namespaces.

## Fixed

- **The artifact transport accepts a cloud deployer's own repository.** 0.24.3 let `app image-plan` accept a destination in the delegation's repository, but the artifact transport still held every cloud app image to the platform repository the context names. The plan observed the deployer's image as an ownership mismatch and refused with a reasonless "required resource observation is unavailable", and publication would have refused next. In a deployer context, observation and publication now accept any repository of the context's project, as `app image-plan` does. Admission still holds the destination to the delegation's image repository. An operator context is unchanged.
- **A cloud deployer's apply passes the project guard.** An apply's project guard inspects Application Default Credentials, and a deployer's bundle carries only its service-account key and gcloud configuration, so every deployer apply refused with "Application Default Credentials could not be inspected". With nothing else set, a deployer's Application Default Credentials are now its bundle key, whose project is the context's, and the guard is unchanged.
- **A cloud deployer's image apply needs no Pulumi.** An apply that publishes an artifact took the operator's infrastructure path, which selects the context's Pulumi stack. A hosted deployer has no Pulumi binary, state or operator credentials, so every deployer image publication refused with "reviewed Pulumi stack is absent or unavailable". A deployer apply with no Pulumi member now keeps the release guard and skips the Pulumi workspace; the artifact transport still asserts the context's project before every observation and publication.
- **A deployer's workload plan no longer refuses as stale.** Admission stamps a deployer's scopes after its lifecycle decisions are validated, and planning compared the decisions with the stamped candidate, so every deployer site or app deploy refused with "lifecycle decisions were validated for a different composition candidate". The decisions now bind to the stamped candidate.
- **A deployer's cluster guard needs no host configuration.** The guard read the expected node from the operator's `hosts/<context>/host.nix`, which a deployer bundle does not carry, so every Kubernetes observation by a hosted deployer was unavailable. With no host configuration, a deployer expects the context's default host name; a context whose host has another name still refuses.
- **A plan prints an artifact ownership refusal's reason.** The transport's ownership reason is a fixed string, so the plan now shows it instead of hiding it with provider output.

## Upgrade notes

No config change is needed. A deployer uses the 0.24.4 CLI.

## Compatibility and rollback

`transitionsFrom` adds 0.24.3. Existing records, journals, reviews and snapshots are unchanged.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work intranet running the candidate.
