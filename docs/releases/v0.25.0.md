# Nagare 0.25.0

A release that changes nothing the intranet runs no longer moves it: the host switches and the
cluster is written only when what they evaluate changes, and the admin API image is rebuilt only when
its own code changes.

## Changed

- **The host moves only when what it evaluates changes.** Every release rewrote the generated
  version comments and the payload store path in the host flake, so every release planned a host
  activation. The host's reviewed identity now leaves the comments out and compares the payload by
  its narHash. The transport still checks the files byte for byte.
- **A release that moves no platform scope leaves the cluster alone.** The plan keeps the version
  marker an earlier release wrote. `platform transition commit` plans again itself and pins such a
  release only when that plan finds no work, still writing the pin last. `platform status` reports
  the cluster as this release when the pin, the accepted scopes and convergence agree, and shows the
  older marker as `clusterStamp`.
- **The admin API reports its serving image (breaking, contract 1).** `GET /v1/platform/version` and
  `nagare.servingBuild` carry `image`, the reference its Deployment starts it with, by digest, and the
  contracts; they no longer carry `version`, `platformVersion` or `revision`. `nagare.comparison`
  sets that image beside the `nagare-admin-api` image of the accepted declaration and carries
  `declaredImage` and `servingImage`. An image reused across releases cannot name the release that
  installed it.
- **The admin API is built from `nagare-core`.** The code it shares with nagarectl, 79 modules, is
  its own package, which embeds no release version and links no planner, adapter or context code.
  A CLI-only change no longer rebuilds the admin API image.
- **The backup collector reads observation bytes only.** A backup CronJob whose accepted bytes exist
  only in a review published before observation bytes is reported unresolved with the remedy
  `nagarectl inventory store materialize-native`; it is never accepted. The CLI keeps its review
  fallback.

## Upgrade notes

No config change is needed. This upgrade switches the host once, because the host's identity is
computed differently. It restarts the admin API once, for its new image and its `--image` argument,
and nagare-access once, because the versions contract it links changed. A later release that
changes only the CLI moves none of them. Deployers move to the 0.25.0 CLI and
re-plan; a review saved with an older CLI is refused at apply. A reader of `/v1/platform/version` or
of `nagare.comparison` reads the new fields.

## Compatibility and rollback

`transitionsFrom` adds 0.24.5. Existing records, journals, reviews and snapshots are unchanged.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work intranet running the candidate.
