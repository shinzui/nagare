# Nagare 0.15.0

Nagare 0.15.0 ships its En, Shōmei, nagare-access and admin API images, so an upgrade moves those
workloads with no Cloud Build run and no hand-edited digest.

## Added

- **Release images.** `release.json` names the four linux/amd64 images by digest and OCI layout store
  path, and names no registry. The candidate pushes them to `shinzui.cachix.org`, publication pins them
  there, and each context publishes them into its own registry during its reviewed transition. Nothing
  is published to GitHub. An operator needs no cache credential or configuration: `nagarectl` fetches a
  layout into a private store only when the registry lacks that image, and checks it against the
  reviewed digest. A cache miss or a wrong layout refuses before any registry change and never compiles.
- **Image status.** `platform status` reports each workload as `release`, `override`, `other-release`,
  `drift`, `unknown` or `not-enabled`, comparing digests of the Pods that are actually serving. Anything
  but `release` or `not-enabled` makes an otherwise exact status `image-skew`, which never blocks the
  reviewed transition that repairs it.

## Changed

- **An image whose inputs did not change keeps its digest.** The images carry no release version, so an
  upgrade leaves an unchanged image alone. The admin API links `nagarectl` and moves with most releases.
- **The candidate refuses operator pins.** A release that names images refuses in preflight, naming the
  variable, while the operator shell exports `NAGARE_AUTH_EN_IMAGE`, `NAGARE_AUTH_SHOMEI_IMAGE`,
  `NAGARE_AUTH_ACCESS_IMAGE` or `NAGARE_ADMIN_API_IMAGE`. Immutable overrides still work for any other
  use and stay reported as overrides.

## Upgrade notes

Remove the four image variables from the context's environment before planning, unless a workload should
keep an override.

En and Shōmei only move forward. Their migration Jobs are named after their images, so naming an image
they have moved away from refuses at planning, before any change. Fix a bad image with a new one, or
restore from the recovery point. `nagare-access` and the admin API have no migrations, so an old image can
be named again.

The release images are linux/amd64. A context on an arm64 host names its locally built images as
overrides. The release rehearsal runs them under Rosetta, so its Colima profile needs `rosetta: true`.

## Compatibility and rollback

`transitionsFrom` adds 0.14.2. The inventory, journal, review and snapshot formats are unchanged. The new
`platform:release-images` scope appears when a context first moves to this release.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work
intranet running the candidate with no image pins.
