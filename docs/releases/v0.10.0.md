# Nagare 0.10.0

Nagare 0.10.0 makes a reviewed change cost seconds: on the work intranet one access grant's plan
went from 43 s to about 6 s and its apply from 67 s to about 11 s. It also keeps protected-site
sessions alive across concurrent token refreshes and Shomei outages.

## Changed

- **A command opens the inventory once and reads it concurrently (MasterPlan 29, BUG-8).** A
  plan opens its store once, reads the head once and loads the accepted history once, and no
  longer lists every object the context ever wrote. An apply loads the history once and admission
  reuses it while the head under the writer lock is unchanged. Cold reads fetch content-addressed
  members eight at a time with one request each, and a review republishes nothing already in the
  local digest cache.
- **The journal is served from a verified local copy.** An apply keeps the committed journal
  events it read in the context's cache, re-reads the newest one from the store to bind the copy,
  and downloads only the events after it; the full hash chain is still checked on every read.
- **One En connection per command.** Access plans, applies, `access check` and `inventory status`
  keep one port-forward and run the cluster guard once per command; owner identities are still
  read before every observation and write.
- **`inventory status` with a cold cache** reads its native evidence eight at a time (45.8 s to
  11.8 s on the intranet).

## Added

- **`NAGARE_TRACE=1`** prints, on stderr when a command ends, each store's opens, gcloud sessions,
  head reads, history loads, remote and cached gets, puts and listings with their time. See
  [inventory operations](../runbooks/inventory-operations.md).

## Fixed

- **Protected-site sessions survive concurrent refreshes and Shomei outages (EP-211).** Concurrent
  refreshes of one token share one Shomei call, and only Shomei's explicit rejection ends a
  session; a transport error, 429, 5xx or unavailable keys answer 503
  (`authentication_unavailable`) and keep the cookies.

## Maintainers

- The release version is written only in `release.json`; the Cabal package versions of
  `nagare-dsl`, `nagarectl`, `nagare-access`, `nagare-contract`, `nagare-api` and
  `nagare-api-server` are now `0.0.0` (breaking for anything that bounds them by version).
- `just release-candidate` moves the intranet to the candidate before the tag, unattended.

## Compatibility and rollback

`transitionsFrom` adds 0.9.0. Nothing written to the inventory store changes: reviews, scope
members and journal events have the same bytes, and the journal copy lives only in the local
cache (`~/.cache/nagare/<context>/inventory-blobs/journal`).

## Known limitations

- The first apply on a workstation without a journal copy reads the whole journal once and writes
  the copy (79 s on the intranet); later applies read only the new events.
- Each command still spends 2 to 3 s creating its gcloud session.
- An older remote journal event corrupted without repairing the chain is not noticed by a client
  whose local copy predates it (ADR 22, 2026-10-22).

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the
work intranet running the candidate.
