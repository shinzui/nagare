# Nagare 0.21.0

Nagare's En upgrades to En `5bb3f80d` and serves operator-declared En tenants beside Nagare's own ([EP-262](../plans/262-upgrade-en-and-serve-operator-declared-en-tenants-from-one-server.md)). A workload can opt out of its app's managed store ([EP-261](../plans/261-scope-an-app-s-managed-env-and-secrets-to-the-workloads-that-reference-them.md), [ADR 38](../adr/0038-a-workload-inherits-its-app-s-managed-store-unless-it-opts-out.md)).

## Added

- **Operator-declared En tenants** ([EP-262](../plans/262-upgrade-en-and-serve-operator-declared-en-tenants-from-one-server.md)). `NAGARE_EN_TENANTS` and one `NAGARE_EN_TENANT_<NAME>_SCHEMA` per tenant give each tenant its own database `en-<name>-db` with backups and restore, a migration Job, its schema and a key Secret `nagare-en-tenant-<name>-keys`. See [En tenants](../user/contexts.md#en-tenants). Only the operator's context declares tenants.
- **`nagarectl en-tenant bind NAME --app APP -f CONFIG`** writes a tenant's keys into the app's managed runtime Secret as one reviewed secret change, the same way `nagarectl secret set` does.
- **En monitoring.** En runs in tenant mode, with Nagare's data as tenant `nagare`. A scrape key in `nagare-en-scrape-keys` reads every tenant's metrics and no tenant's data. vmagent scrapes En, and `EnTenantUnavailable` (VMRule `nagare-auth-alerts`) fires when a tenant's database is unavailable. Apply now proves every declared tenant is available before it finishes.
- **A workload can opt out of its app's managed store** ([EP-261](../plans/261-scope-an-app-s-managed-env-and-secrets-to-the-workloads-that-reference-them.md)). `managedEnv = NoManagedEnv` on a web service, worker or task renders it with no `envFrom` of the managed Runtime ConfigMap and Secret.
- **App-database readers** can declare SELECT-only verification metadata, and bind an explicit relation to an accepted scratch restore of the same app.

## Changed

- In an Application, the web service and the workers now inherit the Application's managed store, as its tasks already did. An Application's worker, and a web service whose name differs from its Application's, change the store their `envFrom` names on the next deploy.
- En's memory limit grows by 128 Mi for each declared tenant.

## Upgrade notes

This release changes `Config.hs` source: a `Deployment`, `Worker` or `Task` record literal must set `managedEnv = InheritManagedEnv`, and an app-database reader record literal must set `exceptions = []`. Existing JSON reader declarations are unchanged. A config that starts from a preset, such as `Nagare.Dsl.Presets.webService`, and overrides fields with record update needs no edit, now or when later releases add fields. A configuration that inherits keeps its rendered bytes and digest.

The upgrade restarts En once, in tenant mode, on the same database. Its relationships and datastore id are unchanged.

## Compatibility and rollback

`transitionsFrom` adds 0.20.0. The platform gains the `nagare-en-scrape-keys` Secret, the `en` VMServiceScrape and the `nagare-auth-alerts` VMRule. Existing records, journals, reviews and snapshots are unchanged.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work intranet running the candidate.
