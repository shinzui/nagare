# Nagare 0.29.0

An application can now have a private object bucket of its own, serve untrusted documents from a
content domain that never receives the login cookie, and sign short-lived tokens with an Ed25519
key set the platform rotates (IR-55, MasterPlan 39). On a cloud context each workload granted a
bucket reaches it through its own keyless Google identity. A plan now refuses another writer's
Kubernetes fields before a review exists, instead of mid-release.

## Added

- **App object buckets** ([guide](../user/object-storage.md)). A bucket is its own document with
  per-prefix expiry rules and per-workload grants (`ReadWrite` or `ReadOnly`, optionally signing
  URLs). `nagarectl bucket plan`, `bucket status` and `bucket retire`; a service, worker, task or
  Application workload binds it and gets its endpoint and credentials as variables. On a local
  context the bucket lives in the packaged MinIO. On a cloud context it is a GCS bucket with
  uniform access and enforced public access prevention, and each grant is its own Google service
  account holding one role on that bucket, reached through workload identity federation with no
  key (ADR 42). Retiring a bucket keeps the bucket and its objects and disables its accounts.
- **Content domains** ([guide](../user/content-domains.md)). `NAGARE_CONTENT_DOMAINS` lists
  registrable domains, separate from the base domain, that one worker may serve as `*.D` and `D`
  with the `Host` header intact. A direct cloud context creates a Cloud DNS zone per domain, and
  the route gets a wildcard certificate through DNS-01. `nagarectl domains check` prints each
  zone's name servers and whether the domain is delegated. Retiring a route says what its
  collection removes, the certificate's private key included.
- **Signing key sets** ([guide](../user/signing-keys.md)). `nagarectl keyset plan` reviews an
  Ed25519 key set whose keys the in-cluster rotator (`nagare-keyset`, in the admin API image)
  generates and rotates on a schedule with an overlap. A `Sign` workload reads `public.json` and
  `private.json`, a `Verify` workload only `public.json`, from files that change in place. No
  review holds a key.
- A review lists what it removes before it is applied.
- `nagarectl inventory plan`, `platform bootstrap plan` and the release transition refuse, at plan
  time, an update to an object whose fields another writer owns (`kubectl patch`, `edit`,
  `annotate`), naming each object, writer and field. `--take-over-fields` (and
  `just release-candidate X.Y.Z --take-over-fields`) opts in to taking them over.

## Fixed

- A local context whose inventory store is its object store resumes, bootstraps and plans
  transitions; they failed with `inventory object store URL must start with gs://`.
- `inventory store status` reports a version-2 head's active transaction and executor claim
  instead of `null`.
- `context env` no longer creates a Pulumi stack on a fresh cloud context, which made the first
  foundation review refuse the stack as owned without history.

## Upgrade notes

No config change is needed. The cloud foundation now enables `sts.googleapis.com` and
`iamcredentials.googleapis.com`, so a cloud context's upgrade plans one foundation update. A cloud
context that declares a bucket needs `NAGARE_PROJECT_NUMBER` in its context file. The `nagare-access` and
admin API images get new digests, the admin API's carrying `nagare-keyset`; each context publishes
them into its registry as it upgrades, and the En, Shōmei and tunnel images keep their 0.28.2
digests. A context that sets `NAGARE_ADMIN_API_IMAGE` keeps its own image and must
name one with `nagare-keyset` before it declares a key set.

## Compatibility and rollback

`transitionsFrom` adds 0.28.2. Context files that set `NAGARE_CONTENT_DOMAINS` are ignored by an
earlier CLI.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work intranet running the candidate.
