# Nagare 0.6.0

Nagare 0.6.0 is the first release an installed context can move to in place
([EP-172](../plans/172-rehearse-candidate-upgrades-of-an-inventory-context-instead-of-rebuilding-it.md)).
It also fixes the findings from bootstrapping the work intranet on 0.5.0: access grants by email,
the access service's address, inline env shadowing, recovery of a partially applied Pulumi stage,
and a clearer refusal on a developer's first prebuilt-image deploy.

This is a pre-1.0 minor release. See [Unmet production targets](#unmet-production-targets) and the
[production-readiness checklist](production-readiness-checklist.md).

## Highlights

- **Upgrade an installed context in place.** `nagarectl platform transition plan --out DIR`
  reviews the next stage that moves an admitted context from its pinned release to this one. Apply
  each with `nagarectl inventory apply DIR --yes` and plan again until the review has no
  operations, then pin the context with `nagarectl platform transition commit --yes`. The first
  admitted stage opens a transition marker in the store head. Until the commit, only this
  release's `nagarectl` applies, resumes, recovers or closes, and every stop resumes from where it
  left off. Cloud scopes are planned again from this payload; an accepted host is re-pinned
  through the reviewed, self-reverting activation (ADR 11) and never re-imaged. The pin moves last.
- **Grant access by email (F96).** `access grant --user` and `access revoke --user` accept a Shomei
  user's email and resolve it to exactly one user id; an unknown or ambiguous email is refused.
- **Access changes reach en privately (F97).** Reviewed grants and revocations go through a
  private port-forward to en, not the address a grant was recorded through. Grants made by 0.5.0
  still bind.
- **`env set` refuses a shadowed key (F98).** A managed env or secret key that the Config also sets
  inline is refused instead of silently losing to the inline value. The auth portal example sets
  no inline literals.
- **A partially applied Pulumi stage closes by proof (F113, F114).** When a provider refuses a
  Pulumi create partway (for example, Cloud DNS's ownership check), `inventory close` settles it
  from the stack export: present members are kept and absent ones proved absent, with no attested
  close. The replan folds an existing member that depends on the create into that create, so it
  no longer fails with an operation dependency cycle.
- **A clearer prebuilt-image refusal (F116).** A reviewed deploy whose rollout image differs from
  the accepted publication names both images and says that a `PrebuiltImage` takes its tag from
  the Config, not from `--tag`. The `--tag` help says the same.
- **Releases bind the upgrade rehearsal.** A release is accepted only with the EP-172 rehearsal
  record: a disposable local context moved from 0.5.0 to this release, with a seeded database row
  read back unchanged.

## Install

```bash
export NAGARE_VERSION=0.6.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

Application developers who do not operate infrastructure may use `#nagarectl` instead.

## Prerequisites

Unchanged from 0.5.0. Nix remains the supported distribution channel. Cloud operations require an
authenticated Google Cloud SDK, Application Default Credentials whose quota project matches the
context project, the context's Pulumi backend and stack configuration, SSH access to the generated
host name, and the matching context kubeconfig. A cloud context's host stage also needs the
context's x86_64-linux builder (`NAGARE_BUILDER_PROJECT`, `NAGARE_BUILDER_ZONE`,
`NAGARE_BUILDER_INSTANCE`).

## Upgrading

Move a context on 0.4.0 or 0.5.0 with the 0.6.0 `nagarectl`:

1. Install 0.6.0, select the context, and check that `nagarectl inventory status --json` reports
   no active transaction.
2. Run `nagarectl platform transition plan --out DIR`, read the review, and apply it with
   `nagarectl inventory apply DIR --yes`. Repeat with a new directory until the plan has no
   operations.
3. Run `nagarectl platform transition commit --yes`. `nagarectl platform status` then reports the
   CLI, payload, context and cluster on 0.6.0.

A stopped stage keeps the marker open; resume, recover or close it with the 0.6.0 `nagarectl`.
Operators who keep their context in a private repository commit the updated host flake lock and
any rewritten configuration together with the new release pin.

Node (NixOS and k3s) and PostgreSQL major upgrades within a context are unchanged.

## Compatibility and rollback

- **Transitions.** `transitionsFrom` lists 0.4.0 and 0.5.0. The 0.5.0 path is rehearsed end to end
  for this release; the 0.4.0 path is held to a frozen v0.4.0 payload and store fixture by the
  test suite.
- **Systems and schemas.** Supported client systems remain `x86_64-linux` and `aarch64-darwin`.
  Asset, host-flake metadata, and platform compatibility schema versions remain 1, and the
  inventory store's head and journal wire versions are unchanged.
- **Rollback.** `rollbackSupportedFrom` remains empty. A transition moves forward only; release
  selection never restores application data.
- **Distribution.** Nix-by-immutable-tag remains the supported channel.

## Unmet production targets

- **Cloud transition stages on a real host.** The 0.5.0 to 0.6.0 rehearsal runs on a local context,
  which has no cloud scopes or host. The first cloud context to move is the work intranet, after
  publication.
- **Deferred findings.** F112, F115, F117, F118 and F119 are deferred to a later release (see the
  [findings tracker](../audits/mp23-findings.md)); F119 is planned as
  [EP-185](../plans/185-make-inventory-status-answer-in-seconds.md).

## Known limitations

- Nagare runs a single node: no high availability, and a database pod restart is brief downtime.
  The agreed recovery-time objective is four hours (ADR 28).
- `inventory status` takes minutes on a full context because it observes every resource live
  (F119).
- All capabilities remain experimental.

## Validation

A green full gate on the candidate (both Haskell suites, the recovery model, the mutation records,
the payload and operator-package boundaries, documentation validation and the full flake checks on
both supported systems), the native output and clone-free rehearsal of each supported system, and
the EP-172 rehearsal record moving a seeded local context from 0.5.0 to this release.
