# Nagare 0.2.1

Nagare 0.2.1 is a safety release for operators of cloud contexts. It fixes defects in 0.2.0 that
made `nagarectl platform upgrade` unsafe, stopped the project guard from working with an installed
release, and let a documented `context create --force` command silently reset a context. **Do not
run `nagarectl platform upgrade` with 0.2.0 on a real cloud context. Use 0.2.1.**

## What was wrong in 0.2.0

- **Missing stack config.** An installed CLI runs Pulumi in a per-release payload workspace, and
  that workspace never contained the context's `Pulumi.<context>.yaml`. `nagarectl context guard`,
  and therefore `just infra-up`, refused with "Pulumi stack '…' declares no gcp:project". Every new
  release got a fresh workspace without values such as `nagare:nagareImageSelfLink`.
- **Unguarded upgrade.** The upgrade's `pulumi-preview` and `pulumi-apply` phases ran in that
  workspace without the stack config, and apply used `pulumi up --yes --skip-preview`. Neither phase
  ran the project guard or the VM-replacement guard.
- **Missing Node dependencies.** Payload workspaces had no `node_modules`, so no real Pulumi
  command could run from an installed release.
- **`--force` reset contexts.** `nagarectl context create NAME --force` reset every omitted field
  to its default, for example `NAGARE_BASE_DOMAIN=apps.example.com` and the default VM shape. The
  Let's Encrypt staging instructions recommended exactly that command. A changed base domain
  replaces the Cloud DNS zone, which gets new name servers and breaks the parent delegation, and
  the replacement guard did not protect the zone.
- **Host version never read.** `nagarectl platform status` reported every generated host as
  `legacy / unknown`, because the version comments in the host flake are indented.

## Changes

- **Context-owned stack config.** The stack config now lives at
  `${XDG_CONFIG_HOME:-$HOME/.config}/nagare/pulumi/Pulumi.<context>.yaml`. Before any Pulumi
  command, Nagare links `Pulumi.<context>.yaml` in the payload workspace, and in a source
  checkout's `infra/pulumi`, to that file.
  - A lone older workspace copy is adopted.
  - Two different copies are refused, with both paths named.
  - A context-owned path that is a symlink to a missing file is refused, because Pulumi would
    otherwise read it as empty configuration.
- **Node dependencies installed.** The first Pulumi command in a workspace runs `npm ci` from the
  release's lock file.
- **Guarded upgrades.** Both Pulumi phases of `platform upgrade` run the project guard and the
  replacement guard, and apply previews again (ADR 18).
- **Wider replacement guard.** `nagarectl infra guard` now refuses to replace the Cloud DNS managed
  zone or a storage bucket, as well as the GCE instance. `NAGARE_ALLOW_VM_REPLACEMENT=1` overrides
  all three for one run. A failed preview now shows Pulumi's error diagnostics.
- **Merging `--force`.** `nagarectl context create NAME --force` changes only the flags you pass,
  keeps every other stored field and the platform pin, and prints the lines that changed.
- **Host identity.** `platform status` reads host release identities correctly.
- **Maintainer changes.** The clone-free release rehearsal ignores the operator's direnv
  environment. CI pushes flake builds to the `shinzui` Cachix cache when `CACHIX_AUTH_TOKEN` is
  configured.

## Install

```bash
nix run github:shinzui/nagare/v0.2.1#nagarectl -- version --json
nix profile install github:shinzui/nagare/v0.2.1#nagarectl
```

## Before your first Pulumi command with 0.2.1

- **Private repository.** If your stack config lives in a private operator repository (ADR 13),
  link it to the context-owned path once. Otherwise the first command refuses when your checkout's
  link points elsewhere:

  ```bash
  mkdir -p "${XDG_CONFIG_HOME:-$HOME/.config}/nagare/pulumi"
  ln -s /path/to/ops/pulumi/Pulumi.<context>.yaml \
    "${XDG_CONFIG_HOME:-$HOME/.config}/nagare/pulumi/Pulumi.<context>.yaml"
  ```

- **Existing workspace copy.** If `context use` seeded the stack config into a 0.2.0 workspace, the
  first 0.2.1 command copies it to the context-owned path.
- **Node.js and npm.** Both must be on `PATH` for Pulumi commands.

Then check the context before any apply:

```bash
nagarectl context guard
nagarectl infra guard      # expect: no GCE instance replacement is planned
```

## Upgrading

- **From 0.2.0.** Nothing in the platform payload's cluster manifests or NixOS modules changed.
  Follow the staged [per-context upgrade](../user/upgrades.md) with the 0.2.1 CLI.
- **From 0.1.0 or a legacy context.** Read the [0.2.0 notes](v0.2.0.md) first. Then upgrade
  directly to 0.2.1 with the 0.2.1 CLI; you do not need to install 0.2.0.

## Compatibility and limits

- **Systems and schemas.** Supported client systems are `x86_64-linux` and `aarch64-darwin`, and
  Nix is the only distribution channel. Asset, host-flake metadata, and compatibility schema
  versions are unchanged at 1.
- **Rollback.** `rollbackSupportedFrom` stays empty. Release selection never restores databases,
  persistent volumes, or Pulumi state.
- **Experimental.** All capabilities remain experimental.

## Validation gaps

The release gates cover unit tests for the link, merge, classifier, and host identity logic. They
also run the clone-free Nix check with a fake Pulumi and npm, and native clone-free rehearsals.
Before release, the linked stack config and guards were exercised read-only against a live cloud
context: `context guard` was confined and `infra guard` found no replacement. The guarded upgrade
phases are verified by a live dry-run plan and apply against that context after publication. They
have no unit test through the upgrade engine.
