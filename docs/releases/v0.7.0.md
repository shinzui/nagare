# Nagare 0.7.0

Nagare 0.7.0 lets many apps share one managed PostgreSQL or ClickHouse server, each confined to
its own databases, users, grants, credentials and backups.

This is a pre-1.0 minor release: a config that builds a `Deployment` or `Worker` record literally
needs one new field. See [0.6.0](v0.6.0.md) for the in-place upgrade and the
[production-readiness checklist](production-readiness-checklist.md).

## Added

- **App databases on shared servers (IR-29).** An *app database* is a reviewed tenant of an
  accepted server: one or more logical databases (exactly one on PostgreSQL), a migration user that
  owns them and a runtime user that reads and writes rows, with explicit grant lists and no access
  to any other app or to the server's own databases. Declare them in a config that calls
  `emitAppDatabases`, then:
  - `nagarectl db app-database plan --config FILE [--save-plan DIR]` provisions them;
  - `nagarectl db app-database rotate NAME --user runtime|migration` rotates one password, Secret
    first;
  - `nagarectl db app-database retire NAME` turns logins and grants off and keeps the data;
  - `nagarectl db app-database list` lists them.

  Workloads bind them with `appDatabases`; a deploy injects only `<name>-runtime`. A server either
  hosts app databases or is bound directly, never both. Each app database has its own signed
  backup schedule `nagare-appdb-<name>` under `app-databases/<namespace>/<name>/`, ingested with
  `db app-database backup-receipts` and restored with `db app-database restore`, into scratch
  databases or, with `--rebuilt`, into the empty databases of a rebuilt server. See
  [Sharing one server between apps](../user/managed-databases.md#sharing-one-server-between-apps)
  and [ADR 30](../adr/0030-app-databases-are-reviewed-tenants-of-a-shared-server.md).

## Changed

- **`Deployment` and `Worker` gain `appDatabases`.** A config that builds either record with
  record syntax adds `appDatabases = []`. Presets (`webService`, `webWorker`) and record updates
  are unaffected, and the field is emitted only when non-empty, so existing workloads keep their
  bytes.
- **ClickHouse servers turn on SQL access management.** Each existing ClickHouse server's
  StatefulSet sees one reviewed update on its next apply and restarts once.

## Fixed

- **Backup and restore Job pods no longer receive database connections.** Their pods carried
  `nagare.dev/database`, the label a server's Service selects, so while a scheduled backup ran a
  share of new connections went to the Job pod and were refused. Job pods now carry
  `nagare.dev/database-job`. Each existing backup CronJob sees one reviewed update.

## Install

```bash
export NAGARE_VERSION=0.7.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

## Upgrading

Move a context on 0.4.0, 0.5.0 or 0.6.1 to 0.6.6 with the 0.7.0 `nagarectl`, as described in
[0.6.0's upgrade steps](v0.6.0.md#upgrading). Expect the transition reviews to update every
database backup CronJob, and every ClickHouse server's StatefulSet, which restarts its pod once.
Then add `appDatabases = []` to any config that builds a `Deployment` or `Worker` literally.

## Compatibility and rollback

`transitionsFrom` adds 0.6.6. Everything else is unchanged from 0.6.6.

## Known limitations

- A retired app database's backup schedule keeps running and fails while its migration login is
  off; dropping a retired app database is not offered.
- A workload binds at most one database per engine across `databases` and `appDatabases`.
- Moving an existing direct consumer onto an app database is a data migration, not a rebinding.
- F126 and F127 remain deferred as in 0.6.6; see the
  [findings tracker](../audits/mp23-findings.md).

## Validation

A green full gate and mutation sweep on the candidate, the native output and clone-free rehearsal
of each supported system, the EP-172 rehearsal record moving a seeded local context from 0.6.6 to
this release, `just local-app-database-smoke` on a local context, and the work intranet upgraded
on the candidate before the tag.
