# Nagare 0.8.0

Nagare 0.8.0 completes what the work intranet needs from app databases on shared PostgreSQL and
ClickHouse servers: reviewed access beyond the fixed grant set, a maintenance window for one app,
and read-only users that other apps bind. It also keeps a scheduled backup recoverable after its
schedule changes.

## Added

- **Reviewed grant exceptions and per-user limits (IR-30, IR-32).** An app database's `access`
  names, for its runtime and migration users:
  - ClickHouse exceptions from a closed allow-list: `system.parts`, `system.mutations`,
    `system.disks`, `system.storage_policies` and `CREATE ARBITRARY TEMPORARY TABLE`;
  - ClickHouse ceilings (`maxMemoryBytes`, `maxExecutionSeconds`, `maxConcurrentQueries`),
    constrained `MIN 1 MAX <value>`, so an app can lower them but never raise them or set `0`;
  - a PostgreSQL connection limit and a default statement timeout;
  - `monitoring = [PgMonitor]`, which tolerates the grants PGMQ's install makes to `pg_monitor`.

  Anything else is refused when the config loads. A change plans an update of that user, and a
  hand change outside the declaration is refused as drift.
- **A maintenance window for one app database (IR-31).** `db app-database quiesce NAME --users
  runtime[,migration]` closes those logins, pauses the backup schedule and drains the app's
  sessions, its scheduled run in flight and, on ClickHouse, its mutations, without restarting the
  shared server or touching another app. `db app-database backup NAME` takes the schedule's own
  Job on demand, ingested, restored and pruned like a scheduled run. `db app-database resume`
  reopens exactly the quiesced users, and `db app-database evidence` prints the window's server
  identity, drain and backup.
- **Read-only readers (IR-33).** An app database declares readers in `access`, each with
  `SELECT` on named tables or views of its own databases (or, on PostgreSQL, every view of a
  schema), fixed ceilings, and the apps that may bind it. A workload in such an app names the
  reader in `appDatabaseReaders` and receives only the reader's Secret. A PostgreSQL view the
  app's migrations have not created yet is pending and printed as a note. A `SECURITY DEFINER`
  function `PUBLIC` may run, or a declared `security_invoker` view, refuses the plan. Readers
  rotate with `db app-database rotate NAME --user reader-<name>` and retire by declaring
  `retired`.

See [Sharing one server between apps](../user/managed-databases.md#sharing-one-server-between-apps).

## Fixed

- **A scheduled run taken before its schedule changed stays recoverable.** Adding a logical
  database to an app database, or moving a server's image, used to leave every earlier run
  impossible to ingest, so its recovery point could not be restored through Nagare, and every
  later prune refused. Any schedule revision Nagare applied now authorizes its runs, and a
  restore loads only the databases the run holds.

## Install

```bash
export NAGARE_VERSION=0.8.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

## Upgrading

Move a context on 0.7.1 to 0.8.0 with the 0.8.0 `nagarectl`, as described in
[0.6.0's upgrade steps](v0.6.0.md#upgrading).

A config that builds a record with record syntax adds the new field; presets (`webService`,
`webWorker`) and record updates are unaffected:

- an `AppDatabase` adds `access = noAppDatabaseAccess`;
- a `Deployment` or `Worker` adds `appDatabaseReaders = []`.
App databases accepted on 0.7.1 decode and plan unchanged until their configs declare access or
readers.

## Compatibility and rollback

`transitionsFrom` adds 0.7.1. Everything else is unchanged from 0.7.1.

## Known limitations

- A reader's consumers are apps in the app database's own namespace.
- A reader stays declared once accepted; retire it instead of dropping it.
- A PostgreSQL reader's role defaults (`default_transaction_read_only`, the statement timeout) are
  advisory; its boundary is its grants.
- A workload binds at most one credential per engine across `databases`, `appDatabases` and
  `appDatabaseReaders`.
- Dropping a retired app database is not offered.

## Validation

A green full gate and mutation sweep on the candidate, the native output and clone-free rehearsal
of each supported system, the EP-172 rehearsal record moving a seeded local context from 0.7.1 to
this release, `just local-app-database-smoke` on a local context, and the work intranet upgraded on
the candidate before the tag.
