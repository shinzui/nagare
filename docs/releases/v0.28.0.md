# Nagare 0.28.0

A context can now choose Attic's chunking threshold, so cache hits on a GCS-backed Nix cache are
redirects to GCS instead of NARs streamed through the cache Pod (BUG-11, EP-278). Hourly backup
schedules no longer all start in the same second (EP-238 M3), and an application can deploy an
existing OCI image by digest.

## Added

- `NAGARE_NIX_CACHE_NAR_SIZE_THRESHOLD`, in bytes, sets Attic's `[chunking] nar-size-threshold`
  for the context's cache. The default is `65536`, as before. `0` stores every newly pushed NAR as
  one object, so a client downloading it gets a presigned GCS redirect. A malformed value is
  refused, and the value is read from the stored context, so a shell variable cannot change it.
  `nagarectl init` and `nagarectl context create` take `--nix-cache-nar-size-threshold BYTES`.
- The Nix cache guide explains the trade-off (whole-NAR storage gives up chunk deduplication, so
  the bucket grows faster) and gives a rehearsed procedure that moves existing chunked NARs to
  whole-object storage without touching the NAR signing key.
- `nagarectl app image-plan --registry-reference REPOSITORY@sha256:DIGEST` reviews an existing
  single-platform OCI manifest in the context's registry, and `inventory image-references
  --contract 1` lists accepted image identities (`image-reference-list`), so `app deploy
  --image-resource ID --tag TAG` can deploy it.

## Changed

- An hourly database, app-database or volume backup CronJob starts at a minute offset derived from
  its name (`M-59/15 * * * *`, M from 0 to 14; 0 keeps `*/15 * * * *`), so a context's backups no
  longer start together every quarter hour. Daily schedules, freshness thresholds and receipts are
  unchanged, and receipts signed under the earlier schedule stay ingestible.

## Upgrade notes

No config change is needed. The `nagare-access` and admin API images get new digests, which each
context publishes into its registry as it upgrades; the En, Shōmei and tunnel images keep their
0.27.0 digests. A context that does not set the variable renders the same Attic server
configuration as 0.27.0, so the upgrade does not restart Attic or rerun its migration. To opt in, add
`export NAGARE_NIX_CACHE_NAR_SIZE_THRESHOLD=0` to the context file and run bootstrap; only new
uploads follow the setting, and the guide's reseed moves the NARs already chunked.

Each hourly backup CronJob whose name gives a non-zero offset gets a new schedule at its next
review, including the upgrade's. A schedule changed by hand with `kubectl patch` stays owned by
that writer, and the update refuses on it with `fields managed by another writer: kubectl-patch`
before writing. Close the stopped transaction, remove the `kubectl-patch` entry from the
CronJob's `metadata.managedFields` (the work intranet's nine hand-staggered schedules were
handled this way), and run the upgrade again.

## Compatibility and rollback

`transitionsFrom` adds 0.27.0. Context files written by 0.28.0 carry the new variable, which an
earlier CLI ignores. Setting the threshold back to `65536` and bootstrapping restores the old layout
for new uploads; NARs stored whole keep working.

## Validation

A green full gate, the EP-172 upgrade rehearsal reading its seeded row back unchanged, and the work intranet running the candidate.
