# Nagare 0.28.0

A context can now choose Attic's chunking threshold, so cache hits on a GCS-backed Nix cache are
redirects to GCS instead of NARs streamed through the cache Pod (BUG-11, EP-278).

## Added

- `NAGARE_NIX_CACHE_NAR_SIZE_THRESHOLD`, in bytes, sets Attic's `[chunking] nar-size-threshold`
  for the context's cache. The default is `65536`, as before. `0` stores every newly pushed NAR as
  one object, so a client downloading it gets a presigned GCS redirect. A malformed value is
  refused, and the value is read from the stored context, so a shell variable cannot change it.
  `nagarectl init` and `nagarectl context create` take `--nix-cache-nar-size-threshold BYTES`.
- The Nix cache guide explains the trade-off (whole-NAR storage gives up chunk deduplication, so
  the bucket grows faster) and gives a rehearsed procedure that moves existing chunked NARs to
  whole-object storage without touching the NAR signing key.

## Upgrade notes

No config change is needed, and every service image keeps its 0.27.0 digest. A context that does not set the variable renders the same Attic server
configuration as 0.27.0, so the upgrade does not restart Attic or rerun its migration. To opt in, add
`export NAGARE_NIX_CACHE_NAR_SIZE_THRESHOLD=0` to the context file and run bootstrap; only new
uploads follow the setting, and the guide's reseed moves the NARs already chunked.

## Compatibility and rollback

`transitionsFrom` adds 0.27.0. Context files written by 0.28.0 carry the new variable, which an
earlier CLI ignores. Setting the threshold back to `65536` and bootstrapping restores the old layout
for new uploads; NARs stored whole keep working.
