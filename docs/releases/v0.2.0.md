# Nagare 0.2.0

Nagare 0.2.0 hardens the operator path found in the pre-flight review of 0.1.0. Every cloud-mutating
path is confined to the active context's project. The ACME identity and VM shape now belong to the
context. Host switches revert themselves when access cannot be verified. Operators can also run
their own authentication portal for protected sites.

This is a breaking pre-1.0 release. Read [Breaking changes](#breaking-changes) before you move a
context from 0.1.0.

## Highlights

- **Authentication portal.** Replace the built-in sign-in and access-error pages with an app you
  own. A reference portal ships in `cluster/examples/auth-portal`, and
  `nagarectl access portal show` reports the registered portal. `nagare-access` keeps ownership of
  every `nagare_*` cookie and strips those cookies before proxying HTTP or WebSocket requests. See
  [Operator-owned authentication portal](../user/auth-portal.md).
- **Project confinement.** `nagarectl context guard` refuses when the selected Pulumi stack, the
  ambient `CLOUDSDK_CORE_PROJECT`, or gcloud's configured project disagrees with the active context.
  `just infra-up` and `just infra-preview` run it first. `nagarectl init` refuses a Pulumi state
  bucket owned by another project, and a state-backend bootstrap failure now fails `init`.
  Bucket-ownership checks in the scripts, and auth-image builds, use the active context's project.
- **Context-owned VM shape.** `NAGARE_MACHINE_TYPE`, `NAGARE_BOOT_DISK_TYPE`,
  `NAGARE_BOOT_DISK_SIZE_GB`, and `NAGARE_DATA_DISK_SIZE_GB` are seeded at context creation and
  projected into Pulumi config. Every ordinary apply previews first and refuses a plan that would
  replace the GCE instance unless `NAGARE_ALLOW_VM_REPLACEMENT=1` is set. The check is
  `nagarectl infra guard`. See [Resizing the VM](../user/resizing-the-vm.md).
- **Self-reverting host switches.** `just host-switch` refuses the in-repo evaluation fixture. It
  also refuses a configuration that does not authorize your SSH key. Before activating, it arms an
  on-host rollback timer and leaves the boot default unchanged. It commits only after a brand-new
  SSH login and `sudo` succeed. GRUB is on the serial console with a ten-second menu and 20
  retained generations. See [Day-2 host changes](../user/day-2-host-changes.md).
- **Data disk grows itself.** Raising `NAGARE_DATA_DISK_SIZE_GB` is absorbed online by
  `x-systemd.growfs`, with no manual `resize2fs`.
- **Clone-free launcher environment.** The installed `nagare` launcher exports the active
  context's Pulumi backend and stack through `nagarectl context env`, so recipes no longer
  inherit whatever Pulumi state the calling shell carried.
- **Managed databases.** StatefulSets gain readiness probes. Scheduled backups wait for the
  database to accept connections, stamp their run time correctly, and survive DNS being
  unavailable during a cold boot.

## Breaking changes

- **Operator secrets are no longer in the repository.** A checkout or payload no longer ships
  `cluster/secrets/` or the `nagare-01` host secret. Put your encrypted cluster manifests under
  `${XDG_CONFIG_HOME:-~/.config}/nagare/cluster-secrets/<context>/`, or set
  `NAGARE_CLUSTER_SECRETS_DIR`. Keep host flakes and sops recipients in your own private
  repository (ADR 13). The observability installer refuses when a required encrypted secret is
  missing.
- **The ACME contact has no default.** Rendering the cert-manager `ClusterIssuer` requires
  `NAGARE_ACME_EMAIL` in the active context, and `NAGARE_ACME_DIRECTORY` selects the endpoint.
  `nagarectl init` refuses non-interactively without `--acme-email`. Add the variable to every
  context created with 0.1.0 before running `just cluster-bootstrap`. See
  [ACME identity](../user/contexts.md#acme-identity).
- **The host-switch contract changed.** `scripts/host-switch.sh` no longer runs
  `nixos-rebuild`. It exits `3` when it would lock the operator out (or the target is the
  evaluation fixture) and `4` when access was not verified. After a `NOT COMMITTED` result, run
  nothing against the host until the rollback window (default 600 seconds) has passed. Automation
  that parsed the old output or exit codes must be updated.
- **The evaluation fixture refuses activation.** Switching any host onto the in-repo
  `nixos#nagare-01` is refused. Switch through your context-owned host flake instead.
- **Haskell record fields were renamed.** The packages now follow `haskell-jitsurei` conventions,
  with semantic, unprefixed field names accessed through generic-lens labels. Typed configuration
  or other Haskell source that names the old prefixed fields must be updated. Serialized JSON,
  rendered manifests, command names and help, and `nagare-access` HTTP behavior are unchanged.

## Install

Inspect the CLI without cloning:

```bash
nix run github:shinzui/nagare/v0.2.0#nagarectl -- version --json
```

For a persistent profile installation:

```bash
nix profile install github:shinzui/nagare/v0.2.0#nagarectl
```

## Upgrading a 0.1.0 context

1. Install the 0.2.0 CLI next to the retained 0.1.0 payload, and run `nagarectl platform status`.
2. Add `NAGARE_ACME_EMAIL` (and `NAGARE_ACME_DIRECTORY` if you do not use Let's Encrypt production)
   to the context.
3. Record the live VM shape in the context. Stacks that predate shape seeding still resolve the
   old fallback literals, but an explicit value keeps a later edit from surprising you. Run
   `just infra-preview` and confirm the guard reports no instance replacement.
4. Move encrypted cluster secrets into the context-owned secret directory.
5. Follow the staged [per-context upgrade](../user/upgrades.md). The regenerated host flake takes
   the new NixOS input. Apply it only through `just host-switch`.

The host input moves nixpkgs to 2026-09-11. That brings Tailscale 1.102.3 (security fixes
TS-2026-004 through TS-2026-011), k3s 1.35.8, and Linux 6.18.51. Journald now sets
`Storage=persistent` explicitly, and Tailscale no longer manages the host's DNS
(`--accept-dns=false`). A host with a hand-locked `/etc/resolv.conf` should be unlocked first, as
described in [Troubleshooting](../user/troubleshooting.md).

## Compatibility and limits

The supported client systems are `x86_64-linux` and `aarch64-darwin`. Nix is the only supported
distribution channel; there are no portable binary archives, Homebrew formulae, or CLI container
images. Asset, host-flake metadata, and compatibility schema versions are unchanged at 1. Cloud
provisioning still requires the operator's GCP authentication, local operation requires Docker,
and operator recipes still expect the third-party clients listed in Getting Started.

`rollbackSupportedFrom` stays empty because the reverse release-selection transaction from 0.2.0
to 0.1.0 has not been tested. Keep the 0.1.0 payload workspace until the upgraded context is
verified. Release selection never restores databases, persistent volumes, or Pulumi state. Stateful
recovery follows the
[disaster-recovery runbook](../runbooks/disaster-recovery.md).

All capabilities remain experimental. The optional Shomei/En authentication plane is still built
from local source checkouts (`SHOMEI_SRC`, `EN_SRC`). The authentication portal was validated on
local k3d. Passkeys in the portal still need the manual trusted-browser ceremony described in its
guide.

## Validation gaps

The release gates cover the flake checks, including the host-switch auto-rollback, boot menu,
data-disk auto-grow, and evaluation-fixture VM checks. They also cover the release-consistency
gate and native clone-free rehearsals on both supported systems. Publication did not exercise
these paths:

- a live 0.1.0 to 0.2.0 context upgrade against a GCP project;
- a live `cluster-bootstrap` issuer render against a production ACME directory; or
- the portal's passkey ceremony in a real browser.

Rehearse those on a disposable context before upgrading one that holds data.
