# Nagare 0.3.0

Nagare 0.3.0 makes a fresh GCP cluster bootstrap reproducible in one documented flow and makes
multi-domain routing, apex DNS, and origin/edge TLS observable and fail-closed. It also hardens
cloud project confinement, reviewed Pulumi applies, first-boot host recovery, context access, and
certificate scope.

This is a breaking pre-1.0 release for Haskell typed-configuration source. Read
[Breaking changes](#breaking-changes) before updating an application configuration or advancing a
context.

## Highlights

- **One-pass GCP onboarding.** The installed operator package can initialize a context, apply the
  exact reviewed Pulumi plans without a TTY, select a context-owned remote builder, wait for a Ready
  first boot, deliver the host age key over IAP, fetch a context-safe kubeconfig, and bootstrap the
  cluster once. A hermetic state-machine rehearsal rejects project, plan, builder, readiness,
  kubeconfig, webhook, and certificate-scope mismatches.
- **Project-confined cloud operations.** Nagare checks the active gcloud project and Application
  Default Credentials quota project before Pulumi. Saved plans are bound to context, project,
  stack, backend, payload, program, and review digest. A never-deployed context can be re-pinned only
  after an exact GCE NotFound proves that its host and cluster do not exist.
- **Reliable first boot and secret delivery.** Blank-disk formatting is ordered before fsck and k3s,
  and mount recovery retries the dependent boot graph. New hosts accept an operator-held age key
  through context-confined IAP SSH stdin, validate its metadata and digest, and retry sops-nix and
  Tailscale activation without rebuilding the image with secrets.
- **Context-safe access.** The operator package no longer exports colliding Haskell `lib/links`,
  includes `socat`, and adds `nagarectl kubeconfig fetch` plus `nagarectl cluster guard` so Kubernetes
  mutation targets the selected context and its sole expected node.
- **Production domain routing.** Applications, static sites, and server sites share a strict
  `DomainSpec` model. Hostname conflicts refuse before apply; deploy waits for DomainMappings and
  their selected TLS policy. `nagarectl domains list --json` reports real DNS, route, issuer, and
  certificate observations, and `nagarectl domains check` is the strict operational gate.
- **Apex and CDN TLS.** Pulumi owns exact and wildcard base-domain records. Google CDN can prepare a
  Certificate Manager DNS authorization, apex-and-wildcard certificate, and certificate map while
  the legacy proxy keeps serving, then activate only after the replacement certificate is ACTIVE.
- **Confined cluster certificates.** Public namespace wildcards require the
  `nagare.dev/app-namespace=true` label. Cluster-local and system-internal certificates stay on the
  self-signed issuer. The payload includes a reproducibly built fix for the issuer-reference alias
  in the final archived net-certmanager v1.14.0 release.
- **Fail-closed bootstrap timing.** Cloud and local bootstrap wait for cert-manager, Knative, and
  net-certmanager webhooks and retry only convergent ConfigMap merge patches within a bounded
  window.

## Breaking changes

- **Static and server typed configurations use `DomainSpec`.** `StaticSite.domains` and
  `ServerSite.domains` changed from `[Domain]` to `[DomainSpec]`, matching ordinary applications.
  Replace an old singleton such as `[domain]` with `unsafeOrEither (mkDomains [(domainText domain,
  True)])`, or construct domain specifications directly. Serialized static/server JSON remains
  backward compatible: legacy string arrays decode with the first hostname canonical and automatic
  TLS.
- **Hostname validation is strict.** Domains are normalized to lowercase ASCII without a trailing
  dot and must be valid RFC 1123-style multi-label hostnames. Wildcards, IP literals, duplicate
  normalized values, Unicode names that are not supplied as IDNA A-labels, and lists without
  exactly one canonical entry are rejected before rendering.
- **Deploy success is stronger.** A production deploy now reads hostname ownership before apply and
  waits for every declared DomainMapping and certificate. Automation that treated Service readiness
  alone as completion should allow for this additional bounded wait and handle explicit conflict or
  TLS diagnostics.

## Install

Platform operators should install the complete operator output:

```bash
export NAGARE_VERSION=0.3.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

Application developers who do not operate infrastructure may use `#nagarectl` instead.

## Prerequisites

Nix is the supported distribution channel. Cloud onboarding additionally requires Node.js with
npm, an authenticated Google Cloud SDK, Application Default Credentials whose quota project matches
the context project, and operator-owned SSH, sops, age, DNS, and ACME inputs. Review the exact target
inventory printed by initialization and every saved Pulumi plan before applying it.

Changing `bootDiskSizeGb` replaces the VM and its boot-resident k3s state; size the boot disk for the
VM lifetime. Raising the separate data-disk size remains a forward-only online growth operation.

## Upgrading

Install the 0.3.0 operator alongside the retained old payload and run:

```bash
nagarectl platform status
```

Then follow the staged [per-context upgrade procedure](../user/upgrades.md). The target release's
CLI stages and reviews Pulumi, host, and Kubernetes changes and advances the context pin last.
Existing contexts retain their Google CDN `legacy` certificate mode. To migrate, preview `prepare`,
wait until `nagarectl cdn status` reports the Certificate Manager certificate ACTIVE, and only then
preview and apply `certificate-map` mode.

The release adds a Pulumi-owned exact base-domain `A` record. Before applying to an existing Cloud
DNS zone, inspect the preview. If an exact apex record already exists outside Pulumi, import that
record into the stack rather than deleting or replacing it blindly.

## Compatibility and rollback

- **Systems and schemas.** Supported client systems remain `x86_64-linux` and
  `aarch64-darwin`. Asset, host-flake metadata, and platform compatibility schema versions remain 1.
- **State and migrations.** No NixOS `system.stateVersion`, Kubernetes storage schema, database
  schema, or persistent-data migration is introduced. Pulumi adds apex DNS and optional Certificate
  Manager resources; review existing-record ownership before apply.
- **Rollback.** `rollbackSupportedFrom` remains empty because a reverse 0.3.0 release-selection
  transaction has not been tested. Selecting an older workstation package does not restore
  infrastructure, DNS, cluster state, databases, or persistent volumes.
- **Distribution.** Nix-by-immutable-tag remains the supported channel. The Cabal packages are not
  published to Hackage by this release.

## Known limitations

- The provider-independent replacement-cutover engine is deliberately not exposed as a mutating
  production command. Its GCE, Kubernetes, candidate-host, and state-transfer adapters and live
  bounded-downtime drills remain future work.
- Google CDN certificate-map mode supports the exact base domain and one-label subdomains. Use
  Cloudflare or separately managed edge infrastructure for unrelated zones or deeper hostnames.
- Canonical domain selection controls the advertised URL; it does not create HTTP redirects from
  alternate names.
- All capabilities remain experimental.

## Validation

The source and native release gates cover the Haskell suites, Pulumi compilation and topology
tests, NixOS first-boot VM samples, installed operator/package boundaries, hermetic one-pass GCP
orchestration and refusal cases, cluster webhook and certificate-policy tests, documentation and
OKF validation, the local three-host trusted-TLS smoke, full flake checks, and clone-free operation
on every supported system. The Release workflow records exact revisions, Nix output identities,
clone-free evidence, and checksums in immutable attachments.
Because the payload now embeds a Linux controller image, the assembled manifest records
`payloadDigests` by supported system; the legacy scalar `payloadDigest` is `null` in that combined
artifact. Each native runner's manifest and `nix-output-<system>.json` retain the exact corresponding
Nix hash.

The release is published only after its candidate CI and non-publishing native Release rehearsal
pass. At candidate cut time, two tag-dependent cloud checks remain deliberately post-publication:
the exact `v0.3.0` upgrade and staging ACME/domain smoke on the authorized `tan-nb-exp` test
installation, and EP-139's stricter from-empty-project rehearsal. The latter cannot be substituted
with `tan-nb-exp` because its stack already contains the test installation. Neither result is
inferred from hermetic evidence.
