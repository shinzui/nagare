# Nagare 0.9.0

Nagare 0.9.0 lets an app database's own users do what real apps need inside their own databases,
such as a PGMQ queue that the server creates at startup. It also fixes a ClickHouse server restart
that blocked every review of the server's app databases.

## Added

- **Privileges inside the app's own databases, and owner workloads (IR-35).** An app database's
  `access.privileges` declares, reviewed like the rest of its access:
  - on PostgreSQL, `CREATE` for the runtime in named schemas of its database (`createIn`, for
    example `pgmq`) or on the database itself (`createSchemas`). Whenever the runtime may own
    objects, the migration user becomes a member of the runtime role, so the scheduled `pg_dump`
    and later migrations reach runtime-owned tables. A declared schema that the app's migrations
    have not created yet is pending and printed as a note.
  - on ClickHouse, any privilege that the running server scopes to a database (`CREATE TABLE`,
    `DROP TABLE`, `ALTER TABLE`, ...) for either user, granted on each of the app's databases. A
    global privilege, or a group that contains one, refuses the plan with
    `app-database-privilege-unknown`.

  `access.owners` names the workloads that bind the migration credential instead of the runtime
  credential, for apps that run their own migrations. Objects a runtime owns outside its declared
  schemas, and every grant outside the declaration, are still drift.

See [Privileges inside the app's own databases](../user/managed-databases.md#privileges-inside-the-apps-own-databases).

## Fixed

- **A ClickHouse server restart no longer blocks its app databases (BUG-7).** ClickHouse 26.8
  accepted the migration user's `WRITE ON FILE` but stored it in the legacy form `FILE ON *.*`.
  After a restart, the server reloaded that as `READ` and `WRITE`. Every plan, quiesce and resume
  of every ClickHouse app database on the server then refused with `app-database-grant-drift:
  <app>_migration: server-wide READ`. Nagare's ClickHouse servers now turn on
  `access_control_improvements.enable_read_write_grants`, so the grant is stored and reloaded as
  written. Every migration user-access block revokes `READ ON FILE`, and a `READ` observed on a
  migration user is pending, not drift. `READ ON FILE` on any other user is still drift.

## Install

```bash
export NAGARE_VERSION=0.9.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

## Upgrading

Move a context on 0.8.0 to 0.9.0 with the 0.9.0 `nagarectl`, as described in
[0.6.0's upgrade steps](v0.6.0.md#upgrading).

- **Update each ClickHouse server once; it restarts.** The release transition does not touch
  database servers. After it commits, run the server's own create command again as a standard
  update, for example `nagarectl db create clickhouse NAME --config CONFIG --recovery-backup
  BACKUP --recovery-key-version VERSION --save-plan DIR`, and apply the review. It updates the
  server's ConfigMap, which gains the setting, and its StatefulSet, whose pod template gains a
  `nagare.dev/config-digest` annotation that rolls the pod whenever the config changes.
- **Each ClickHouse app database plans one update per migration user afterwards.** The restart
  reloads the old storage form once. The next `db app-database plan`, or a `resume` of a quiesced
  app database, revokes the reloaded `READ` with reason `keeps server-wide READ`. After that, the
  grant survives further restarts as written.
- **Literal `AppDatabaseAccess` records add the new fields.** A config that builds
  `AppDatabaseAccess` with record syntax adds `privileges = noDatabasePrivileges` and
  `owners = []`. Configs that start from `noAppDatabaseAccess` and use record updates are
  unaffected.

App databases accepted on 0.8.0 decode and plan unchanged until their configs declare privileges or
owners.

## Compatibility and rollback

`transitionsFrom` adds 0.8.0. Everything else is unchanged from 0.8.0.

## Known limitations

- A runtime-owned object in a schema removed from `createIn` refuses the plan until a migration
  reassigns or drops it.
- A reader's consumers are apps in the app database's own namespace.
- A reader stays declared once accepted; retire it instead of dropping it.
- A workload binds at most one credential per engine across `databases`, `appDatabases` and
  `appDatabaseReaders`.
- Dropping a retired app database is not offered.
