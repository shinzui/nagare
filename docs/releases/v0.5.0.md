# Nagare 0.5.0

Nagare 0.5.0 closes the intranet gaps 0.4.0 left open
([EP-183](../plans/183-close-the-intranet-gaps-left-by-v0-4-0-https-login-volume-backups-retention-and-service-rebuild.md)).
Developers can deploy an application behind protected HTTPS login. Application volumes are
backed up on the database schedule. Scheduled backups are kept and pruned under the agreed
retention. A lost database or volume can be rebuilt from its last verified recovery point.

This is a pre-1.0 minor release. See [Unmet production targets](#unmet-production-targets) and the
[production-readiness checklist](production-readiness-checklist.md).

## Highlights

- **Protected HTTPS login for every deploy.** The access enforcer now re-reads its route map
  every five seconds. A route protected after the platform bootstrap is served without restarting
  the enforcer. Before, it answered 502 "no backend configured" until the enforcer was rolled.
  A DomainMapping served over plain HTTP while its certificate is pending no longer counts as
  ready. `nagare-harness route-check` checks a protected route over verified HTTPS: it requires
  the anonymous login redirect, a refused wrong CA, and the reviewed grant and revoke.
- **Scheduled volume backups (D2).** Every backup-included application volume gets a scheduled
  producer (`nagare-volbackup-<app>-<volume>`) that uploads signed receipts on the database
  schedule. `server status` grades each volume's freshness against the context's recovery-point
  objective. `storage backup-receipts APP VOLUME (--backup-id ID | --all)` ingests runs, and
  `storage restore APP VOLUME RUN_ID --scheduled-run` restores an accepted run into a scratch
  claim.
- **Retention and prune (D4).** The agreed policy
  ([ADR 28](../adr/0028-the-intranet-stays-single-node-with-hourly-recovery-points-and-a-four-hour-rebuild.md))
  keeps every run for 48 hours, then one a day for 30 days, and always keeps the newest verified
  run. `server status` warns on runs past retention. `db prune-scheduled-backups` and
  `storage prune-scheduled-backups` review the prune; a stopped prune has one reviewed recovery,
  and it never removes the newest verified recovery point. `db backup-receipts --all` ingests
  every verified run in one review.
- **Rebuild of a lost durable member.** `inventory rebuild-decisions` and `inventory rebuild`
  recreate a missing database or volume as a new incarnation from its predecessor's verified
  recovery point, recording the lineage. `db restore-rebuilt` and `storage restore-rebuilt`
  restore its data.
- **Local MinIO images.** Fresh local contexts bind the locally published MinIO images by default
  and refuse the quay.io pins that no longer answer anonymous pulls.

## Install

After publication, platform operators install the complete immutable operator output:

```bash
export NAGARE_VERSION=0.5.0
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

Application developers who do not operate infrastructure may use `#nagarectl` instead.

## Prerequisites

Unchanged from 0.4.0. Nix remains the supported distribution channel. Cloud operations require an
authenticated Google Cloud SDK, Application Default Credentials whose quota project matches the
context project, the context's Pulumi backend and stack configuration, SSH access to the generated
host name, and the matching context kubeconfig.

## Upgrading

An admitted inventory context cannot change platform version in place (ADR 6). Install 0.5.0 on a
fresh context. To keep data from a 0.4.0 context, restore it into the fresh context from its
verified backups; the reviewed in-place transition between releases is
[EP-172](../plans/172-rehearse-candidate-upgrades-of-an-inventory-context-instead-of-rebuilding-it.md).

Node (NixOS and k3s) and PostgreSQL major upgrades within a context are unchanged from 0.4.0 and
remain drilled in sections 3 and 4 of the checklist.

## Compatibility and rollback

- **Systems and schemas.** Supported client systems remain `x86_64-linux` and `aarch64-darwin`.
  Asset, host-flake metadata, and platform compatibility schema versions remain 1.
- **New formats.** Volume runs use signed v5 receipts, and the retention policy is bound in the
  release. A 0.4.0 context has neither, which is one more reason upgrades go through a fresh
  context.
- **Rollback.** `rollbackSupportedFrom` remains empty.
- **Distribution.** Nix-by-immutable-tag remains the supported channel.

## Unmet production targets

- **Platform upgrade in place.** Moving a context with data to the next release needs a fresh
  context and a restore until EP-172 lands.
- **Native retention check.** The retention warning and prune are proven by the recovery model and
  mutation records, not yet on a running context; a run becomes prunable only after 48 hours.
- **Deferred findings.** Volumes of standalone services and workers are not yet backed up, and
  offline (escrow-only) verification of volume runs that were never ingested is not supported. A
  Service's default host is not yet held to the certificate wait; protected and custom-domain
  routes are.

## Known limitations

- Nagare runs a single node: no high availability, and a database pod restart is brief downtime.
  The agreed recovery-time objective is four hours (ADR 28).
- The 0.4.0 limitations F89 and F94 remain (see the
  [findings tracker](../audits/mp23-findings.md)).
- All capabilities remain experimental.

## Validation

The source and native release gates cover the Haskell suites, the recovery model under every
single fault, the mutation records, payload and operator-package boundaries, clone-free rehearsal,
documentation validation, and full flake checks on the supported systems. The release manifest
binds a local acceptance run (a fresh k3d context) and a cloud acceptance run (a fresh GCP context
with a Let's Encrypt certificate) to this source revision and payload digest; each run's
`inventory-evidence.json` lists its assertions.
