# Nagare 0.6.4

Nagare 0.6.4 serves a context's recorded state through a read-only admin API behind the login
gateway, gives the CLI's outputs a versioned JSON contract, lists a context's recorded sites
without asking providers, makes ClickHouse 26.8 the default for new databases, and fixes preview
identity collisions and cleanup.

This is a pre-1.0 patch release. See [0.6.0](v0.6.0.md) for the in-place upgrade and the
[production-readiness checklist](production-readiness-checklist.md).

## Highlights

- **Read-only admin API (MasterPlan 28).** `https://admin.<base domain>/v1/…` serves the inventory
  head, scopes, recorded sites, image publications and recorded grants. Every list is a Relay
  connection, every 200 has a strong `ETag`, and every error is an RFC 9457 problem. The OpenAPI 3.1
  document is `docs/api/openapi.json`, also served at `/v1/openapi.json`. A person's session cookie
  or a Shomei service account's bearer token both work, and either needs an ordinary
  `nagarectl access grant` on the hostname. It is opt-in per context with
  `NAGARE_ADMIN_API_ENABLED=1`. A cloud context also needs the dedicated read-only reader account
  (`enableAdminApiReader`) and its key in the context's sops secrets
  ([admin API reader](../runbooks/admin-api-reader.md)). The server can read only the inventory's
  head, format and scope objects, and it never writes. See [the admin API](../api/README.md).
- **Gateway answers API clients as an API.** The access gateway now answers these requests with a
  problem document instead of a login redirect:
  - a request on an API backend's `/v1` paths;
  - a request with a bearer credential;
  - a request whose `Accept` prefers JSON (including `+json` types and quality values).

  The problems are 401 with `WWW-Authenticate: Bearer`, 403, 503 when authorization is unavailable,
  and 502/504 when the upstream is down or slow. All are `no-store`, and none carries the HTTP
  client's exception text. An authorizer that takes more than 5 s is unavailable, never a denial.
- **Versioned CLI documents (EP-192).** `--contract 1` prints the documents of the
  [document contract](../api/README.md): inventory status, publications, transaction outcomes,
  saved reviews, image publications and deploy previews. Refusals are problem documents with
  stable codes.
- **`nagarectl site list` (EP-193).** It lists a context's recorded sites, services and (with
  `--include-previews`) previews, from one read of the inventory. It never inspects a provider. Use
  `--json` or `--contract 1` for machine output.
- **ClickHouse 26.8 by default (EP-199).** A new ClickHouse database without an explicit version
  gets `clickhouse-server:26.8`, along with its backup and restore jobs. An explicit version is
  kept, and an accepted database is not upgraded by the default changing.
- **Preview identity and cleanup fixes (EP-195, F99, F100, F101).** Site and preview identities
  can no longer collide, and an over-long preview hostname is refused before it waits forever for a
  certificate. A preview route that never became ready now has a reviewed removal, and cleanup
  skips a member it cannot collect instead of stopping there.
- **Clearer stops (F94, F107, F118).** An ambiguous stop prints the adapter's reason. An expired
  gcloud login asks for reauthentication. `inventory status` explains a workspace that was never
  prepared.

## Install

```bash
export NAGARE_VERSION=0.6.4
nix profile install "github:shinzui/nagare/v${NAGARE_VERSION}#nagare"
nagarectl version --json --tools
nagare --list
```

Application developers who do not operate infrastructure may use `#nagarectl` instead.

## Prerequisites

Unchanged from 0.6.3. An admin API context needs its image, built from this release with
`cluster/bootstrap/auth-images/build-local-image.sh nagare-admin-api` and bound through
`NAGARE_ADMIN_API_IMAGE`, like the auth plane's images.

## Upgrading

Move a context on 0.4.0, 0.5.0, 0.6.1, 0.6.2 or 0.6.3 with the 0.6.4 `nagarectl`, as described in
[0.6.0's upgrade steps](v0.6.0.md#upgrading). A context that does not enable the admin API gets no
new scope. A context that enables it gets scope `platform:admin-api` in the platform stage. The
gateway picks up the API's backend entry without a restart. A local context can enable the API
only for a cluster created with it, because the store mount is part of the cluster. A review
planned by an earlier release does not apply with 0.6.4; plan again.

## Compatibility and rollback

`transitionsFrom` adds 0.6.3, the release the intranet runs, and keeps 0.4.0, 0.5.0, 0.6.1 and
0.6.2. Inventory scopes gain the backend role `api`, which only the admin API scope uses. The
supported systems and schema versions are unchanged, `rollbackSupportedFrom` remains empty, and
Nix-by-immutable-tag remains the supported channel.

## Known limitations

As in 0.6.3, F112, F115, F117, F119 and F120 remain deferred (see the
[findings tracker](../audits/mp23-findings.md)). The admin API reports recorded state only: no live
health or effective-access checks. Machine tokens cannot be revoked before they expire.

## Validation

A green full gate and mutation sweep on the candidate, the native output and clone-free rehearsal
of each supported system, and the EP-172 rehearsal record moving a seeded local context from 0.6.3
to this release. The admin API drill (`scripts/admin-api-drill.sh`) proved the deployed API on a
disposable local context. It covered the browser and service-account paths, the gateway's
problems, gateway-bypass refusal from application and platform pods, and warm latency through the
gateway. The work intranet's upgrade from 0.6.3, with the admin API and its cloud reader, follows
publication.
