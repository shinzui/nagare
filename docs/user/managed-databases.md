# Managed databases

> 🟡 **In progress.** Built and dry-run-verified end to end (typed model,
> renderer, `nagarectl db` CLI, app connection-env injection, backups/restore).
> The full **live** end-to-end run is pending only because `nagare-01` is often
> `TERMINATED`. The in-pod GCS auth that backups depend on is **fixed** (a `/32`
> metadata route + MASQUERADE on the node, and `hostAliases` on the backup Jobs —
> verified live, with the litestream sidecar resumed).

For **app developers** whose app needs a database — PostgreSQL, Redis, or
ClickHouse. You declare a database in typed config; Nagare provisions a durable,
single-replica database with generated credentials, wires it into your app by
name, and backs it up to GCS on a schedule.

A database is **not** an app `Deployment` and **not** a Knative Service. It is a
long-lived `Database` value you provision and operate through the `nagarectl db`
command group.


## The smallest thing that works

```bash
# Provision a Postgres database (generates a password, a Secret, a PVC, a
# StatefulSet, a ClusterIP Service, and a daily backup CronJob):
nagarectl db create postgres pg-main --size 10Gi

# In your app's nagare/Config.hs, reference it by name (databases = ["pg-main"]).
# Then deploy — the app receives DATABASE_URL (a Secret reference) automatically:
nagarectl deploy -f nagare/Config.hs
```

Your app reads `process.env.DATABASE_URL` (or `os.environ["DATABASE_URL"]`) and
connects. The password is never in your config, your image, or a log — it lives
only in a Kubernetes Secret and is delivered to the app by reference.


## Concepts

- A **managed database** is a long-lived database process Nagare runs for you,
  declared as a typed `Database` (engine, version, namespace, size, resources,
  retention).
- A **StatefulSet** is the Kubernetes controller for a workload with a stable
  identity and durable storage. Unlike a Knative Service it does **not** scale to
  zero and keeps the same pod name and disk across restarts. It is the substrate
  for a single-replica database.
- A **ClusterIP Service** is the in-cluster DNS name other pods use to reach the
  database — e.g. `pg-main.personal.svc.cluster.local`. It is internal only;
  databases are never exposed to the public internet.
- A **managed credential Secret**, named `nagare-db-<name>`, holds the generated
  password and the composed connection URL. The password is generated once by
  `nagarectl db create` (the typed DSL is pure and cannot generate randomness)
  and lives only in the Secret. Apps read it by reference, never by copying it.
- A **retention policy** says what happens to the data disk when the database is
  deleted: `Retain` (keep the PVC and its data — the default) or `Delete`
  (destroy it). This is independent of GCS backups.

> **Three hard constraints, up front.**
> - **Single replica on a single node.** No high availability, no replication, no
>   failover — a database pod restart is brief downtime. This is the deliberate
>   single-node design the whole PaaS accepts.
> - **ClickHouse needs explicit memory limits** on the small `e2-standard-2` VM,
>   or it will destabilize the node. The renderer caps it (a `config.d`
>   `max_server_memory_usage` of ~1.5 GiB) and you should also set a container
>   memory limit in `resources`.
> - **Databases are ClusterIP-only** — reachable in-cluster, never on the public
>   internet. To reach one from your workstation, `kubectl port-forward`; do not
>   create a public DomainMapping.


## Declaring a database in `Config.hs`

A database is typed and validated at load time — a bad name, a malformed size, or
an unpinned/`latest` version is rejected with a precise message. The password is
**not** here; it is generated by `nagarectl db create`.

```haskell
{-# LANGUAGE OverloadedStrings #-}

module Main (main) where

import Data.Bifunctor (first)
import Nagare.Dsl.Config (emitDatabase)
import Nagare.Dsl.Database (Database (..), Engine (..), mkDatabaseName, mkEngineVersion)
import Nagare.Dsl.Types (RetentionPolicy (..), defaultNamespace, mkQuantity)

database :: Either String Database
database = do
  name' <- first show (mkDatabaseName "pg-main")
  ver'  <- first show (mkEngineVersion Postgres "18")   -- pinned image tag
  size' <- first show (mkQuantity "10Gi")
  pure
    Database
      { dbName    = name'
      , engine    = Postgres
      , version   = ver'
      , namespace = defaultNamespace          -- "personal"
      , size      = size'
      , resources = Nothing                   -- set memory limits for ClickHouse
      , retention = Retain                     -- keep the data disk on `db delete`
      }

main :: IO ()
main = case database of
  Left err -> ioError (userError err)
  Right db -> emitDatabase db
```

You don't strictly need a config file: `nagarectl db create postgres pg-main`
builds and validates the same `Database` from the command line, with per-engine
defaults (modern major version, `10Gi` size, `Retain`). Use a `Database.hs` +
`db create <engine> <name> --config nagare/Database.hs` when you want the
declaration checked into the repo.


## Choosing an engine, version, size, and retention

The platform defaults to **modern engine majors**, all verified on the cluster:

| Engine | `engine` | Connection port | Data path | Default `version` |
| --- | --- | --- | --- | --- |
| PostgreSQL | `Postgres` | 5432 | `/var/lib/postgresql/data` | `"18"` |
| Redis | `Redis` | 6379 | `/data` | `"8"` |
| ClickHouse | `ClickHouse` | 9000 (native; 8123 HTTP also exposed) | `/var/lib/clickhouse` | `"25.8"` (LTS) |

- `size` is the data PVC (e.g. `"10Gi"`), reusing the `Quantity` convention; it
  becomes a `local-path` `ReadWriteOnce` volume on the node's data disk.
- `resources` (optional) sets CPU/memory requests and limits on the engine
  container. **For ClickHouse, set a memory limit** (see the constraint above).
- `retention` is `Retain` (keep the disk on `db delete`) or `Delete` (remove it).
  GCS backups are a separate mechanism.


## Provisioning and operating: `nagarectl db`

```text
nagarectl db list                  # table of all managed databases in a namespace
nagarectl db create ENGINE NAME    # generate creds + provision Secret, PVC, StatefulSet, Service, CronJob
nagarectl db get NAME              # detail: engine, version, host, retention, ready, Secret key names
nagarectl db shell NAME            # interactive psql / redis-cli / clickhouse-client inside the pod
nagarectl db restart NAME          # roll the StatefulSet pod and wait for ready
nagarectl db delete NAME --yes     # delete, honoring RetentionPolicy (guarded by --yes)
nagarectl db backup NAME           # logical dump to GCS, keep-last-N retention
nagarectl db restore NAME BACKUP_ID  # restore a backup, scratch-first
```

`db create` generates the `nagare-db-<name>` Secret, then applies the PVC,
ClickHouse memory ConfigMap (ClickHouse only), Service, and StatefulSet, then
waits for the rollout. It is **idempotent** and never regenerates the password on
re-run. Resources are discovered by the `nagare.dev/managed-by: nagarectl` +
`nagare.dev/database: <name>` labels, so `db list`/`get` always reflect what was
provisioned.

You can see exactly what `db create` will apply, with no cluster, via `--dry-run`:

```bash
nagarectl db create postgres pg-main --dry-run
```

```text
--- Secret manifest ---
{"apiVersion":"v1","kind":"Secret","type":"Opaque","metadata":{"name":"nagare-db-pg-main", ...
--- PersistentVolumeClaim manifest ---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nagare-db-pg-main-data
  ...
--- Service manifest ---
apiVersion: v1
kind: Service
metadata: { name: pg-main, ... }
spec:
  type: ClusterIP
  ports: [{ name: postgres, port: 5432, targetPort: 5432 }]
--- StatefulSet manifest ---
apiVersion: apps/v1
kind: StatefulSet
spec:
  replicas: 1
  template:
    spec:
      containers:
      - name: postgres
        image: postgres:18
        ...
--- Backup CronJob manifest ---
kind: CronJob
spec:
  schedule: 17 3 * * *
  concurrencyPolicy: Forbid
  ...
Would create database pg-main (postgres) at pg-main.personal.svc.cluster.local
```

`db delete NAME` (without `--yes`) prints the deletion plan and the retention note
and deletes nothing; with `--yes` it removes the StatefulSet, Service, Secret, and
ConfigMap, and — only when `retention = Delete` — the data PVC.


## Connecting an app to a database

Add the database's name to your app's `databases` list in its `Config.hs`:

```haskell
deployment = do
  dep <- webService "notes" "us-west1-docker.pkg.dev/tan-nb-exp/nagare/notes"
  pure dep { databases = [ unsafeName "pg-main" ] }   -- the database this app uses
  where
    unsafeName n = either (error . show) id (mkDatabaseName n)
```

At deploy time, `nagarectl deploy` resolves each referenced database to its
in-cluster DNS host and its managed Secret, and injects the per-engine connection
variables into the app's container. Variables that embed the password (the
composed `*_URL` and any `*_PASSWORD`) are injected as **Kubernetes Secret
references** (`valueFrom.secretKeyRef` into `nagare-db-<name>`), never as inline
values. Host/port/user/db are plain literals.

| Engine | Literals (inline) | Secret references (`secretKeyRef` → `nagare-db-<name>`) |
| --- | --- | --- |
| Postgres | `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_DB` | `POSTGRES_PASSWORD`, `DATABASE_URL` |
| Redis | `REDIS_HOST`, `REDIS_PORT` | `REDIS_PASSWORD`, `REDIS_URL` |
| ClickHouse | `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_USER` | `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_URL` |

The host is the ClusterIP DNS name `<name>.<namespace>.svc.cluster.local`. A
rendered `deploy` shows, for a Postgres reference:

```yaml
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: nagare-db-pg-main
              key: DATABASE_URL
        - name: POSTGRES_HOST
          value: pg-main.personal.svc.cluster.local
        - name: POSTGRES_PORT
          value: "5432"
```

> **An app and its database must share a namespace** (the default `personal`) for
> the DNS name and the Secret reference to resolve. Generated connection variables
> **override** any same-named variable you set yourself. Referencing two databases
> of the same engine is rejected at deploy (both would want `DATABASE_URL`).


## Backups and restore

Every `nagarectl db create` provisions a **daily, self-pruning CronJob** that
backs the database up to GCS — a managed database is backup-included by default
(unless `retention = Delete`, which marks it throwaway). Take one on demand:

```bash
nagarectl db backup pg-main
gsutil ls gs://tan-nb-exp-nagare-backups/databases/pg-main/
```

The dump is an engine-appropriate logical export (`pg_dump` for Postgres, an RDB
dump for Redis, a native dump for ClickHouse), gzipped, at
`gs://tan-nb-exp-nagare-backups/databases/<name>/<timestamp>.<ext>`, with
keep-last-N retention (`--keep`, default 7).

Restore is **scratch-first**: by default the dump is loaded into a disposable
target (`<db>_restore_scratch` for Postgres/ClickHouse) so live data is untouched
until you compare and promote manually. Pass `--into-live` to target the live
database.

```bash
nagarectl db restore pg-main "$(gsutil ls gs://tan-nb-exp-nagare-backups/databases/pg-main/ | tail -1)"
```

See [Backups and disaster recovery](backups-and-disaster-recovery.md) and the
[disaster-recovery runbook](../runbooks/disaster-recovery.md) for the full restore
drill and procedure.

> **In-pod GCS auth (fixed 2026-06-10).** Earlier, in-pod GCS upload was blocked
> because k3s/flannel's IPv4LL `169.254.0.0/16` addresses hijacked the GCE
> metadata IP `169.254.169.254` into the VXLAN overlay (the litestream sidecar
> failed the same way). The fix, in `nixos/hosts/nagare-01/networking.nix`, pins a
> `/32` metadata route to the primary NIC (which always beats the `/16`) plus a
> MASQUERADE so pod traffic is SNAT'd to the node; the backup/restore Jobs also
> carry a `hostAliases` entry so gcloud/gsutil resolve `metadata.google.internal`.
> Verified live (host + in-pod `gsutil`; litestream resumed). The route is applied
> on the running node and committed to NixOS — a `just host-switch` (or the next
> image rebuild) persists it across reboots.


## Constraints and limits

- **Single replica / single node.** No HA, replication, or failover. A database
  pod restart is brief downtime; the StatefulSet identity and the durable PVC mean
  data survives the restart. This is the same single-node trade-off apps accept.
- **ClickHouse memory.** ClickHouse assumes it owns most of the host RAM; on the
  shared `e2-standard-2` it must be capped. The renderer mounts a `config.d`
  `max_server_memory_usage` cap (~1.5 GiB) and you should also set a container
  memory limit via `resources` (see the ClickHouse example).
- **ClusterIP-only.** Databases are never exposed to the public internet. Reach
  one from your workstation with `kubectl port-forward`, not a DomainMapping.
- **Out of scope:** major-version upgrades, in-place engine migration, connection
  pooling as a managed feature (run your own pooler), and multi-tenant users.


## Worked examples

Three runnable end-to-end examples live under `cluster/examples/`, one per engine:

- **[`postgres-app`](../../cluster/examples/postgres-app/)** — a managed Postgres
  database plus an app that reads `DATABASE_URL`, writes a row, and survives a

Each example's `README.md` walks through provision → reference → deploy → back up,
with the offline `--dry-run` renders and the on-VM live commands.

To run scheduled maintenance against a managed database — a nightly cleanup, an
hourly aggregation — declare a [scheduled task](scheduled-tasks.md) on the app that
references the database. The task inherits the app's image and its injected
`DATABASE_URL`, so it reaches the same database; see the
[`app-cleanup-task`](../../cluster/examples/app-cleanup-task/) example.
