Nagare / 流れ   ·   System architecture

One small platform.
One coherent inventory.

Nagare runs many personal applications on a single rebuildable host. Typed, independently owned resource scopes compose into a context-wide inventory, so every change can be checked, reviewed, applied, and explained as one bounded transaction.

Target architectureSingle-node personal PaaSCloud + local modesMasterPlan 23 assumed complete

The whole system

01 / overview

The operator-facing CLI sits above a typed inventory and provider adapters. The deployed platform remains deliberately small: one GCP VM in cloud mode, or k3d on a laptop in local mode.

The inventory is the control plane

02 / change path

A scope is one owner’s complete declaration and revision. Composing all scopes produces the context view and catches conflicting claims before mutation. A review binds the exact candidate, observations, and native provider plans.

1. CompileTyped declarations, capability references, reservations, and graph checks establish valid membership.
2. ReviewObserved facts and provider-native previews are retained under an exact review digest.
3. AdmitOne writer rechecks the base generations and preconditions before effects begin.
4. ResumeJournal receipts let a later run recover and skip operations already proved complete.

Independent owners, shared truth

03 / resource model

The context inventory is a composed view, not a new document with its own release cycle. Platform and application scopes own different resources; authorized app contributions can affect a platform-owned shared object without taking ownership of it.

Deletion is explicit. Omission from a selected scope is not an instruction to remove a resource. Retirement, adoption, transfer, replacement, and migration are reviewed lifecycle decisions bound to identity and recovery policy. Durable data defaults to retention.

What the inventory manages

04 / runtime

Native systems keep their own responsibilities. Nagare’s inventory defines ownership and review across them, while the runtime remains a compact stack on one machine.

Resources across every layer

05 / coverage

A managed resource is more than a Kubernetes object. Nagare declares cloud infrastructure, host state, cluster components, applications, data, credentials, published artifacts, and release controls through the same ownership vocabulary. One provider operation may reconcile several declared resources.

The inventory describes ownership, dependencies, and policy; Pulumi, NixOS, Kubernetes, Helm, storage, and registries remain the authorities for native execution semantics.

Every managed declaration carries
  • A stable logical ID and provider address or claim.
  • An owner scope, executor, desired content, and sensitivity policy.
  • Consumption, readiness, and operation-order relationships.
  • Lifecycle and data recovery policy, plus bounded delegation where needed.
Three declaration roles
  • Managed: Nagare owns and may reconcile the resource.
  • External: a typed capability used but owned elsewhere.
  • Observed child: a bounded controller-produced incarnation that must not collide with another claim.
  • Operation: a closed, reviewed action such as backup or migration, not arbitrary shell text.

Three changes, one protocol

06 / worked paths

The same compiler, reviewer, store, and journal support small app changes and platform-wide work. The selected scope determines what may advance; dependencies identify the native operations required.

APP SCOPE

Deploy a service with a database

An app’s typed configuration and separately versioned environment intent compile into a complete application scope. Its database bundle includes workload objects, credential template, PVC, and backup operation; its image publication and route contribution are explicit dependencies.

  1. Compose against current platform and other app scopes. A Knative-generated Service reservation can reveal a collision with a database Service before any write.
  2. Observe only relevant cluster, artifact, and shared configuration facts; prepare exact native manifests and publication evidence.
  3. Review image, workload, data, backup, route, and secret-reference changes together. Under the lock, admit the current base, publish the image, apply dependencies, verify readiness, and journal receipts.
  4. App B and the platform’s base revision remain unchanged. Only authorized shared configuration content changes.
PLATFORM SCOPES

Upgrade the platform

A selected immutable payload changes the relevant cloud, host, cluster, artifact, and control scopes. The inventory composes them with unchanged application declarations, so a platform update cannot accidentally erase app-owned resources.

  1. Bind the payload identity and compile all selected component declarations; verify cluster render membership and Pulumi registration parity.
  2. Prepare saved native plans and exact render bytes. Review replacements, readiness gates, and any bounded preparation that needs earlier outputs.
  3. Admit a single-writer transaction, run operations in dependency order, and record provider verification after each effect.
  4. Archive inventory and review digests, scope revisions, receipts, and final observations under the payload and run identities.
LIFECYCLE

Retire an application safely

Retiring an app is an explicit change, not a missing file. The lifecycle planner evaluates owner history, current physical identity, dependents, data policy, and the requested deletion decision.

  1. Remove or update the app’s owned workloads and authorized contributions; preserve unrelated scopes.
  2. Retain its database, volume, broker data, backup objects, and recovery credentials unless separately reviewed policy permits collection.
  3. Review any exact deletion targets and native preconditions; refuse if observations are unknown, identity changed, or dependents remain.
  4. Journal the outcome. Retained resources stay visible in status after the original app scope is retired.

State, review, and recovery

07 / transaction store

A review is evidence against a snapshot, not permission to write. Admission rechecks the current head and live preconditions while holding the context writer lock. Intent is journaled before effects; completion is recorded only after adapter verification.

The review barrier

The public review contains redacted declarations and decisions. Private, immutable native bytes live in the context store. Apply resolves and verifies those bytes, then rechecks generations, reservations, and live preconditions under the lock. A changed Pulumi plan, Helm render, or Kubernetes object needs a new review.

One executor at a time

Cloud state uses conditional writes and an executor claim to refuse another workstation. A takeover is explicit; there is no lease or liveness detector. The local store provides process exclusion on one machine. Neither implementation is a distributed coordinator.

Identity and lifecycle

08 / status to retirement

Nagare distinguishes the stable resource a user intends from the particular provider object currently realizing it. That distinction makes renames, transfers, replacement, and retained data explainable without treating names or labels as ownership proof.

Context / scope / resource ID
A context is the managed target. A scope is an independently revised owner declaration. A ResourceId is minted from a stable logical key and role, never from a provider name.
Physical incarnation
The exact VM, Kubernetes UID, bucket, release, or other provider identity observed at a point in time. One logical resource may have active, candidate, and retained incarnations.
Claim and reservation
A provider address, alias, hostname, route, or deterministic controller child that an owner reserves. Retained and unresolved incarnations still hold claims.
Revision and digest
A digest identifies content; a scope revision adds historical generation. A shared resource’s effective digest follows composed content, not the platform owner’s generation.
Typed capability
A reference to a specific exported capability and witness. Sharing a string name with a resource cannot satisfy a dependency or grant authority to mutate it.
Observed status
A timestamped account of identity, owner, dependencies, drift, health, and retirement constraints. Missing and inaccessible remain different outcomes; status does not repair.
Transitions with proof
  • Adopt: explicitly bind a legacy object after provider identity and ownership checks.
  • Transfer or rename: preserve logical identity through a reviewed transition.
  • Replace or migrate: track candidate and retained incarnations with explicit dependency and recovery points.
  • Collect: delete only an exact, historically owned incarnation when dependents and policy permit it.
Data is protected
  • Databases, volumes, brokers, backups, keys, and recovery credentials default to retention.
  • A restore names backup and target identities, fences writes, and specifies forward recovery.
  • Unknown observations cannot prove absence or justify credential regeneration.
  • An interactive maintenance session is journaled and followed by re-observation; arbitrary SQL effects are not claimed as preplanned.

Operational guarantees

09 / boundaries
01 / VALIDITY

Conflicts stop at composition

Typed identities, capability references, provider claims, dependency cycles, and reserved controller children are checked across every scope before external mutation.

02 / REVIEW

Effects match evidence

The candidate digest, observations, and retained native plans or renders form the review. Changed provider output or changed preconditions require a new review.

03 / RECOVERY

Work survives interruption

Immutable snapshots, a durable journal, and operation receipts preserve history. Resume verifies what completed and continues only the remaining authorized work.

Identity and lifecycle
  • Logical ID persists through provider renames and owner transfers.
  • Physical identity names an active, candidate, or retained incarnation.
  • Unknown observation never proves absence or authorizes adoption.
  • Deletion requires exact identity, history, and reviewed retirement policy.
Control boundaries
  • Cloud state uses conditional writes and an explicit single executor claim.
  • Local state uses a private filesystem store with one process writer.
  • Credentials stay in private adapter inputs and never enter public review evidence.
  • Provider tools retain native semantics; the inventory is not a replacement engine.
