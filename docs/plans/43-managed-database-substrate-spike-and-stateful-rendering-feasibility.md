# Managed-database substrate spike and stateful rendering feasibility

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.


## Purpose / Big Picture

Today, Nagare can only run *stateless* workloads. The one and only thing the platform's
renderer (`cli/nagare-dsl/src/Nagare/Dsl/Render.hs`) produces is a **Knative Service** — the
Kubernetes object kind `Service` in the API group `serving.knative.dev/v1` (abbreviated `ksvc`)
that scales to zero pods when idle and back up when a request arrives. That is exactly the wrong
shape for a database: a database is a long-lived process that must never scale to zero, must keep
a stable network identity, must own a durable disk, and needs generated credentials that a pure,
deterministic configuration language cannot produce. MasterPlan 7 (`docs/masterplans/7-persistent-storage-for-nagare.md`)
gave apps a durable `local-path` PersistentVolumeClaim, and MasterPlan 5 gave them managed Secrets,
but there is still no first-class way to declare and run a *database*. The only stateful pattern in
the repository is `cluster/examples/sqlite-litestream/`, a hand-written plain `Deployment` with an
`emptyDir` and a Litestream sidecar — not a managed, typed database.

This plan (**EP-43**) is the **feasibility spike** and the de-risking gate for the whole "Managed
Databases for Nagare" initiative (MasterPlan 9, `docs/masterplans/9-managed-databases-for-nagare.md`).
It is the practical root of that initiative: nothing downstream is allowed to encode a *guess* about
what the cluster will accept. The spike runs all three target engines — **PostgreSQL**, **Redis**, and
**ClickHouse** — on the live single-node k3s cluster, by hand, from raw Kubernetes manifests, and
proves four things per engine: the engine *starts*; it is *reachable* from another pod in the cluster
over stable in-cluster DNS; its *data survives a pod restart* (delete the pod, the controller recreates
it, the same disk re-mounts, the row/key/table is still there); and a per-engine *backup command* works.
For ClickHouse it additionally proves the engine fits inside the small `e2-standard-2` VM (≈8 GB RAM,
2 vCPU) once memory is constrained.

What someone "gains" after this plan is not a feature a user can click — it is a **settled architecture
and a body of verified evidence**. Concretely, after EP-43 the next plan (`docs/plans/44-typed-database-model-and-stateful-statefulset-service-pvc-and-secret-renderer.md`,
EP-44) can write its renderer and golden tests against *verified* YAML shapes recorded verbatim in this
plan's "Interfaces and Dependencies" section, rather than against an unverified hypothesis. The spike
settles the open architectural questions the MasterPlan flagged: StatefulSet versus plain Deployment;
standalone PVC versus a StatefulSet `volumeClaimTemplates` entry; the credential-generation architecture
(the password is generated by the CLI at create time, never by the pure DSL, and lives only in a managed
Secret named `nagare-db-<name>`); the exact ClusterIP Service shape that gives stable internal DNS and is
*never* public; ClickHouse's viable resource limits; and the per-engine backup command. Those verified
shapes and decisions *are* the MasterPlan's Integration Points **IP2** (rendered stateful shapes) and
**IP3** (the credential Secret contract). You can see the spike "working" by reading the captured
transcripts in Concrete Steps: a `psql`/`redis-cli`/`clickhouse-client` session that writes data, a
`kubectl delete pod`, and a second session showing the same data still present.

This plan owns essentially nothing that *ships* in code. Its only optional committed artifact is a set
of example manifests under a spike directory (`cluster/examples/db-spike/`) kept as house-style reference;
its real output is the verified facts and decisions written into *this file*. Everything applied to the
cluster lives in a disposable namespace (`db-spike`) that a single command tears down.

## Decision Log

Record every decision made while working on the plan.

- Decision: Run a throwaway, hand-applied spike on the live single-node cluster to prove all three
  engines (Postgres, Redis, ClickHouse) start, are reachable in-cluster, survive a pod restart with
  data intact, and back up — *before* EP-44 commits any renderer or golden files.
  Rationale: Nagare has only ever rendered Knative Services; a database needs a fundamentally
  different substrate, and ClickHouse's viability on the small `e2-standard-2` VM is a genuine open
  question. The parent MasterPlan (`docs/masterplans/9-managed-databases-for-nagare.md`) gates the
  whole initiative on this de-risking, mirroring how MasterPlan 7 isolated its Knative-PVC spike
  (EP-33, `docs/plans/33-knative-pvc-enablement-spike-and-cluster-feature-flags.md`). The ExecPlan
  specification explicitly encourages an isolated prototyping spike to de-risk significant unknowns.
  Date: 2026-06-10

- Decision (working assumption, to be CONFIRMED in M1–M4): run each database as a single-replica
  Kubernetes **StatefulSet**, not a Knative Service and not a plain Deployment.
  Rationale: a database is a long-lived, stable-identity, durable-storage workload; Knative scales to
  zero (wrong) and a plain Deployment has no stable pod name or ordered storage lifecycle. A
  StatefulSet gives a stable pod name (`<name>-0`), an ordered single-writer rollout
  (`OnDelete`/`RollingUpdate` with one replica), and first-class PVC ownership. The spike confirms
  this is what the cluster accepts and that a pod restart re-mounts the same disk.
  Date: 2026-06-10

- Decision (working assumption, to be CONFIRMED in M1): use a **standalone PVC** (reusing MasterPlan 7's
  `local-path`/`ReadWriteOnce` convention, but named with a dedicated database prefix
  `nagare-db-<name>-data` rather than the app-volume `nagare-vol-<app>-<vol>` name) rather than a
  StatefulSet `volumeClaimTemplates` entry. EP-44 owns this helper as `dbPvcName` (see
  `docs/plans/44-typed-database-model-and-stateful-statefulset-service-pvc-and-secret-renderer.md`).
  Rationale: MasterPlan 7's verified PVC primitive, naming, labels, and `local-path` reclaim behavior
  are already tested and discovered by `nagarectl storage` commands; a standalone PVC keeps databases
  consistent with that and keeps the data disk discoverable and independently retainable. A
  `volumeClaimTemplates` entry would create a PVC named `<vct>-<sts>-0` outside that convention and
  outside `storage list`/`inspect`. The spike tries the standalone PVC first; if the StatefulSet
  controller objects, it falls back to `volumeClaimTemplates` and records why.
  Date: 2026-06-10

- Decision: generate the database password in the **CLI at create time** (EP-45), never in the pure
  DSL, and store it only in a managed Kubernetes Secret named `nagare-db-<name>` carrying labels
  `nagare.dev/managed-by: nagarectl`, `nagare.dev/database: <name>`, `nagare.dev/engine: <engine>`,
  with engine-specific keys (Postgres: `POSTGRES_PASSWORD`/`POSTGRES_USER`/`POSTGRES_DB`/`DATABASE_URL`;
  Redis: `REDIS_PASSWORD`/`REDIS_URL`; ClickHouse: `CLICKHOUSE_PASSWORD`/`CLICKHOUSE_USER`/`CLICKHOUSE_URL`).
  This is MasterPlan IP3. The StatefulSet wires its required env from that Secret.
  Rationale: the typed DSL is pure and deterministic and cannot hold or generate secrets; the password
  is a runtime credential referenced by both the database StatefulSet and consuming apps via Secret
  references. The spike *verifies each engine actually picks up its password from the env/config keys
  the Secret will hold*, so EP-44 encodes a contract the engine honors rather than a guess.
  Date: 2026-06-10

- Decision: databases get a **ClusterIP Service** giving stable in-cluster DNS
  `<name>.<namespace>.svc.cluster.local`, and are **never** exposed publicly (no DomainMapping, no
  Knative route, no NodePort/LoadBalancer).
  Rationale: a database is reached only by other in-cluster pods (apps, backup Jobs). MasterPlan 9 fixes
  "exposing a database to the public internet" as explicitly out of scope. ClusterIP is the minimal,
  internal-only Service.
  Date: 2026-06-10

- Decision: use the disposable namespace `db-spike` for everything the spike applies, so a single
  `kubectl delete namespace db-spike` removes it; spike artifacts (if committed at all) live under
  `cluster/examples/db-spike/` as house-style reference only.
  Rationale: mirrors EP-33's `ep33-spike` namespace pattern; keeps the spike fully reversible and
  guarantees no drift into the real `personal` namespace.
  Date: 2026-06-10

- Decision: run every cluster operation **on the VM via `sudo k3s kubectl`** (or, where a local tool is
  required, via an SSH-forwarded 6443), never against the workstation's default kubectl context.
  Rationale: per the project memory note, IAP forwards only SSH/22 so a workstation kubectl cannot reach
  the k3s API directly, and the workstation's default context points at an unrelated GKE cluster
  (`tan-cluster`/`sennari`). Running on the VM is the simplest correct path for a hand-applied spike.
  Date: 2026-06-10

## Context and Orientation

Read this section fully before running anything. It assumes you know nothing about this repository.

**The cluster and how you reach it.** Nagare is a single-node personal PaaS running on one Google
Cloud Compute Engine virtual machine named **`nagare-01`** (an `e2-standard-2`: 2 vCPU, ≈8 GB RAM),
in GCP project **`tan-nb-exp`**, region **`us-west1`**, zone **`us-west1-a`**. The VM runs NixOS, and
on top of NixOS runs **k3s**, a lightweight single-binary Kubernetes distribution. "The cluster" means
this one-node k3s. The repository root has a `CLAUDE.md` that mandates a hard rule: **every `gcloud`
operation in this repo targets project `tan-nb-exp` only** — never any other project, not even for
read-only listing. Scripts include a preflight assertion that refuses to run if the active gcloud
project is not `tan-nb-exp`, and every `gcloud` call passes `--project=tan-nb-exp` explicitly. This
spike respects that rule for the one place it touches GCS (the optional backup-upload check).

**Critical access reality (do not skip).** Two facts from the project memory note govern how you reach
the cluster. First, the VM is **often `TERMINATED`** to save cost — you must **start it first** and wait
~1–2 minutes for sshd and k3s. Second, **a workstation `kubectl` cannot reach the k3s API directly**:
IAP (Google's Identity-Aware Proxy, the tunnel this repo uses to reach the VM) forwards only SSH on port
22, so opening an IAP tunnel to the k3s API port 6443 is refused, and the workstation's default kubectl
context points at an *unrelated* GKE cluster (`tan-cluster`/`sennari`) that you must **never** touch.
The simplest correct path, and the one this plan uses throughout, is to **run cluster operations on the
VM itself as `sudo k3s kubectl ...`**. You SSH in with the repo's IAP wrapper as the `deploy` user with
the `~/.ssh/id_ed25519` key:

```bash
SSH_USER=deploy SSH_KEY=~/.ssh/id_ed25519 scripts/iap-ssh.sh ssh nagare-01 -- '<command>'
```

If you instead need a *local* tool (for example to upload to GCS from a desktop), SSH-port-forward 6443
over the port-22 tunnel and point `KUBECONFIG` at a copy of `/etc/rancher/k3s/k3s.yaml` with `server:`
rewritten to `https://127.0.0.1:16443` (the k3s serving cert includes `127.0.0.1`, so TLS validates).
This plan does not require that; it runs `psql`/`redis-cli`/`clickhouse-client` *inside the cluster* via
`kubectl exec` and `kubectl run`, so no client tools need installing anywhere.

**The existing renderer, and why it is the wrong shape for a database.** The file
`cli/nagare-dsl/src/Nagare/Dsl/Render.hs` is the platform's only renderer. Its public entry point
`renderService :: Deployment -> Text -> ByteString` turns a typed `Deployment` into a Knative `Service`
YAML document. It already knows how to render a `local-path` `ReadWriteOnce` PVC (the helper
`renderPersistentVolumeClaims`, which stamps labels `nagare.dev/managed-by: nagarectl`,
`nagare.dev/app=<app>`, `nagare.dev/volume=<vol>` and names the claim `nagare-vol-<app>-<vol>` via
`pvcName`), how to mount it (`volumeMountsField`/`volumesField`), and how to pin a volume-bearing
Service to a single always-on replica with the annotations `autoscaling.knative.dev/min-scale: "1"`,
`autoscaling.knative.dev/max-scale: "1"`, and `serving.knative.dev/rollout-duration: "0s"` (the helper
`volumeAnnotationPairs`, verified by EP-33). The renderer serializes through `Data.Yaml.Pretty.encodePretty`
with an explicit key comparator (`knativeConfig`/`keyCompare`/`ranks`) so the YAML key order is
deterministic. **A database is not a Knative Service**: it must not scale to zero, must not have an HTTP
route, and needs a StatefulSet. EP-44 will add a *new* renderer
(`cli/nagare-dsl/src/Nagare/Dsl/Database/Render.hs`) producing StatefulSet + Service + PVC + Secret; this
spike fixes the exact YAML shapes that renderer must reproduce. This plan touches **no Haskell code**.

**The storage substrate, reused from MasterPlan 7.** The cluster's built-in **`local-path` StorageClass**
satisfies a PVC by carving a per-PVC directory out of the host data disk at `/var/lib/nagare/local-path`
on `nagare-01`. It supports only the **`ReadWriteOnce` (RWO)** access mode ("mountable read-write by a
single node"), which is fine because Nagare is single-node. EP-33 verified that data written into such a
PVC survives a pod restart and that the per-PVC directory is named `pvc-<uid>_<namespace>_<pvcname>` and
is reclaimed when the PVC is deleted (the `local-path` default reclaim policy is `Delete`). This spike
reuses exactly that PVC primitive for database data, mounting it at each engine's data path.

**The backup bucket, reused from MasterPlan 7.** There is one GCS bucket for backups,
**`gs://tan-nb-exp-nagare-backups`** (a Pulumi output, `backupBucket`, defined in
`infra/pulumi/src/components/NagarePerimeter.ts`). The VM's attached service account holds
`roles/storage.objectAdmin` on it. **In-pod GCS auth** uses Application Default Credentials resolved via
the node service account; because pods cannot resolve `metadata.google.internal` by name on this cluster,
the working pattern (used by `cluster/examples/sqlite-litestream/deployment.yaml` and `scripts/backup-postgres.sh`)
is to set the env var `GCE_METADATA_HOST=169.254.169.254` so the Google ADC library finds the metadata
server by IP. The existing `scripts/backup-postgres.sh` already dumps a Postgres with `pg_dump | gzip` and
uploads to this bucket, and shows the project-isolation preflight header this repo requires — read it; the
spike's Postgres backup command mirrors it. MasterPlan 9 fixes the database backup layout as
`gs://tan-nb-exp-nagare-backups/databases/<name>/<timestamp>.<ext>` (EP-47 productizes it); the spike only
needs to *prove a dump works*, optionally uploading one object to that prefix to confirm in-pod ADC.

**The existing stateful example, for tone and contrast.** `cluster/examples/sqlite-litestream/` is the
only stateful pattern in the repo today: a plain `Deployment` (`replicas: 1`, an `app: sqlite-litestream`
label selector) with an `emptyDir` data volume and a Litestream sidecar that ships the SQLite WAL to GCS.
Its header comment says outright "a real app would use a PVC on the data disk (local-path)." A managed
database is the disciplined, typed version of "a real app would use a PVC": a StatefulSet with a real
`local-path` PVC, a ClusterIP Service for a stable name, and generated credentials in a Secret. Read that
example's `deployment.yaml`, `litestream.yml`, and `README.md` for the house style of cluster examples
(concise header comments explaining *why*; copy-pasteable `kubectl` blocks). The `db-spike` manifests in
this plan follow that style.

**The engine baseline this spike must VERIFY (plan around it, then refine it).** The MasterPlan supplies
these starting facts; the spike confirms or corrects each, and records the confirmed values in Interfaces
and Dependencies:

- **PostgreSQL** — image `postgres:16` (pin a specific patch tag observed on the cluster, e.g.
  `postgres:16.3`). TCP port 5432. Data directory `/var/lib/postgresql/data`; set `PGDATA` to a
  *subdirectory* such as `/var/lib/postgresql/data/pgdata` so the engine does not trip over the `lost+found`
  directory a fresh ext4-backed PVC may contain. Required env: `POSTGRES_PASSWORD` (mandatory),
  `POSTGRES_USER`, `POSTGRES_DB`. Connection URL: `postgresql://USER:PASSWORD@HOST:5432/DB`. Client: `psql`.
  Backup: `pg_dump | gzip`.
- **Redis** — image `redis:7` (pin, e.g. `redis:7.2`). TCP port 6379. Data directory `/data`. Auth via the
  server flag `--requirepass <password>`. Persistence: RDB snapshots (`BGSAVE`/`SAVE`) and/or AOF. URL:
  `redis://:PASSWORD@HOST:6379`. Client: `redis-cli`. Backup: `SAVE`/`BGSAVE` then copy `dump.rdb`, or
  `redis-cli --rdb`.
- **ClickHouse** — image `clickhouse/clickhouse-server:24` (pin, e.g. `clickhouse/clickhouse-server:24.3`).
  TCP ports 9000 (native protocol) and 8123 (HTTP). Data directory `/var/lib/clickhouse`. The image honors
  env `CLICKHOUSE_USER`/`CLICKHOUSE_PASSWORD`/`CLICKHOUSE_DB`. **Memory risk (the headline ClickHouse
  unknown):** ClickHouse is memory-hungry and will, by default, assume it owns most of the host's RAM;
  on an 8 GB shared VM it MUST be constrained or it will starve k3s, Knative, and the apps. The spike MUST
  determine viable limits — a container `resources.limits.memory` plus a ClickHouse setting
  `max_server_memory_usage` (or `max_server_memory_usage_to_ram_ratio`) — so ClickHouse coexists. URL:
  `clickhouse://USER:PASSWORD@HOST:9000`. Client: `clickhouse-client`. Backup: evaluate `clickhouse-client
  --query "BACKUP ..."` vs. the external `clickhouse-backup` tool vs. native `SELECT ... INTO OUTFILE ...
  FORMAT Native` per table — pick the one viable on the small VM.


## Plan of Work

The work is five milestones. M0 is preparation (start the VM, create the disposable namespace). M1–M3 are
one engine each: apply the four manifests (Secret, PVC, StatefulSet, ClusterIP Service) by hand on the live
cluster, prove in-cluster connectivity, prove data survives a pod restart, and prove a backup command. M4
settles and records the architecture decisions and the verified shapes as the input artifact for the rest
of the initiative, then tears down. The milestone order matters: M1 (Postgres) is the richest and
establishes the full pattern (StatefulSet + standalone PVC + Secret-fed env + ClusterIP + restart-survival
proof + dump); M2 (Redis) and M3 (ClickHouse) reuse that pattern and add only their engine-specific
wrinkles (Redis's `--requirepass`; ClickHouse's memory tuning). Everything M1–M3 applies lives in the
`db-spike` namespace and is throwaway evidence; the only durable output is what gets written into *this*
plan.

A note on the **password** used during the spike. The real architecture (IP3, Decision Log) is that
`nagarectl db create` generates a strong password at create time and stores it in `nagare-db-<name>`. The
spike does not run the CLI (that is EP-45); to verify each engine *picks up* its password from the Secret
keys, the spike hand-creates the Secret with a **fixed throwaway password** (e.g. `spikepw12345`). This is
acceptable because the namespace is disposable and never public; the *point* being proved is the wiring
(env-from-Secret → engine honors it), not password strength.

### Milestone M0 — Prepare the cluster and the disposable namespace

Scope: start the VM, confirm the cluster is healthy, create the `db-spike` namespace. At the end of M0 a
single `Ready` node is visible via `sudo k3s kubectl get nodes` and the `db-spike` namespace exists. No
database objects yet. Acceptance: `sudo k3s kubectl get ns db-spike` shows the namespace `Active`.

### Milestone M1 — Postgres proof (StatefulSet + Service + PVC + Secret, by hand)

Scope: establish the full stateful pattern with Postgres. Apply, in order, a Secret
(`nagare-db-pg-spike`, keys `POSTGRES_PASSWORD`/`POSTGRES_USER`/`POSTGRES_DB`/`DATABASE_URL`), a standalone
PVC (`nagare-db-pg-spike-data`, `local-path`/RWO/`5Gi`), a single-replica StatefulSet running
`postgres:16` with `PGDATA=/var/lib/postgresql/data/pgdata` and its required env wired *from the Secret* via
`envFrom`/`secretKeyRef`, and a ClusterIP Service `pg-spike` exposing 5432. At the end of M1 the database
pod `pg-spike-0` is `Running`/`Ready`; a client pod connects via `psql` over
`pg-spike.db-spike.svc.cluster.local`; a table and a row exist; deleting the pod and letting the StatefulSet
recreate it leaves the row intact; and a `pg_dump | gzip` produces a non-empty dump.

Acceptance (captured transcripts in Concrete Steps): `psql -c "SELECT * FROM spike;"` returns the inserted
row *both* before and after `kubectl delete pod pg-spike-0`; `kubectl get pvc nagare-db-pg-spike-data`
shows `Bound`/RWO/`local-path`; the dump file is `>0` bytes. Optionally, one object appears under
`gs://tan-nb-exp-nagare-backups/databases/pg-spike/` to prove in-pod ADC.

### Milestone M2 — Redis proof

Scope: repeat M1's pattern for Redis. Secret `nagare-db-redis-spike` (keys `REDIS_PASSWORD`/`REDIS_URL`),
PVC `nagare-db-redis-spike-data` (`local-path`/RWO, `/data`), StatefulSet running `redis:7` with the server
started as `redis-server --requirepass "$REDIS_PASSWORD" --save 60 1 --appendonly no` (password sourced from
the Secret env), ClusterIP Service `redis-spike` exposing 6379. At the end of M2: `redis-cli -a` authenticates
(and an *unauthenticated* command is rejected, proving `--requirepass` is honored from the Secret); a key is
`SET`; the pod is deleted and recreated; the key survives a `GET` (because RDB persistence wrote `dump.rdb`
to the PVC). Acceptance: `GET spike:key` returns the set value after the pod restart; an unauthenticated
`GET` returns `NOAUTH`/`ERR`. Record the chosen backup command.

### Milestone M3 — ClickHouse proof, including memory tuning (the hard one)

Scope: repeat the pattern for ClickHouse **and answer the memory question** so the engine coexists on the
8 GB VM. Secret `nagare-db-ch-spike` (keys `CLICKHOUSE_PASSWORD`/`CLICKHOUSE_USER`/`CLICKHOUSE_URL`), PVC
`nagare-db-ch-spike-data` (`local-path`/RWO, `/var/lib/clickhouse`), StatefulSet running
`clickhouse/clickhouse-server:24` with credentials from the Secret AND a memory constraint: a container
`resources.limits.memory` (start at `2Gi`) and a ClickHouse server setting capping its own memory (mount a
tiny config file setting `max_server_memory_usage_to_ram_ratio` or an absolute `max_server_memory_usage`,
or set it so the engine respects the cgroup limit), ports 9000 + 8123, ClusterIP Service `ch-spike`. At the
end of M3: ClickHouse starts and stays up *without evicting or starving* the rest of the cluster (check node
memory pressure and that existing `personal`-namespace pods stay `Running`); `clickhouse-client` creates a
`MergeTree` table, inserts rows; the pod is deleted and recreated; a `SELECT count(*)` returns the same row
count; and a backup approach is chosen and demonstrated. Acceptance: row count survives the restart, node is
not under memory pressure (`kubectl top node` / `kubectl describe node` shows no `MemoryPressure` and the
ClickHouse pod is within its limit), and a backup file/command is recorded. This milestone is where the
spike's hardest unknown is resolved; if ClickHouse cannot be made to fit, that is itself a finding to record
prominently (and a flag back to the MasterPlan).

### Milestone M4 — Settle the architecture and record it; tear down

Scope: turn the M1–M3 evidence into the decisions and verified shapes the rest of the initiative consumes.
Finalize the Decision Log entries (StatefulSet vs Deployment — confirm or revise; standalone PVC vs
`volumeClaimTemplates` — confirm or revise; ClickHouse limits — fix the numbers; per-engine backup commands —
fix the commands; the restart/rollout finding — note any single-writer / `OnDelete`-vs-`RollingUpdate`
concern). Write the **per-engine verified YAML shapes verbatim** into "Interfaces and Dependencies" — these

## Idempotence and Recovery

Every step is safe to repeat. `kubectl apply -f` on the manifests is idempotent: re-applying an unchanged
manifest reports `unchanged`/`configured` and leaves the cluster in the same state. Re-running a `psql`
session that uses `CREATE TABLE IF NOT EXISTS` and a fresh `INSERT` simply adds another row (the proof only
needs *a* surviving row, so duplicate rows are harmless); if you want a clean re-run, `TRUNCATE` the table
first or recreate the namespace. Re-running the Redis and ClickHouse writes is likewise harmless (`SET`
overwrites; ClickHouse `INSERT` appends — assert with `WHERE id = 1` rather than `count(*)` if you have
re-run inserts).

The spike is fully disposable. Everything M1–M3 creates lives in the `db-spike` namespace. If anything goes
wrong mid-spike, run `sudo k3s kubectl delete namespace db-spike` and start over from M0 step 2. Deleting the
namespace cannot affect any other workload because nothing else uses it; in particular it never touches the
real `personal` namespace. If the namespace gets stuck `Terminating` (EP-33 saw this when Knative finalizers
lingered — StatefulSets and PVCs do not have that problem, but PVCs can hold the namespace briefly), delete
the StatefulSets and PVCs explicitly first: `sudo k3s kubectl -n db-spike delete statefulset --all` then
`sudo k3s kubectl -n db-spike delete pvc --all`, then delete the namespace.

Reclamation caveat. The `local-path` StorageClass default reclaim policy is `Delete`, so deleting the PVCs
(directly or by deleting the namespace) removes their host directories under `/var/lib/nagare/local-path`.
That is the desired cleanup for a throwaway spike. The real "keep data on delete" behavior is the typed
`RetentionPolicy` (Retain vs Delete) the model carries (IP1), exercised by EP-45's `db delete`, and out of
scope here.

ClickHouse OOM recovery. If the ClickHouse pod restarts (non-zero `restartCount`) or the node shows
`MemoryPressure`, lower `max_server_memory_usage` in the `ch-spike-mem` ConfigMap and/or adjust the
container `resources.limits.memory`, re-apply the document, and re-run M3 step 2. Record the working
numbers — they are the ClickHouse fact EP-44 encodes. If no configuration makes ClickHouse fit acceptably
alongside the rest of the cluster, that is a first-class finding: record it prominently in Surprises &
Discoveries and Outcomes, and flag it back to the MasterPlan (it may change ClickHouse's scope or default
size).

GCS safety. The only GCS write is the optional probe in M1 step 4, to
`gs://tan-nb-exp-nagare-backups/databases/pg-spike/`. It is small, isolated under a spike-named prefix, and
removed by the cleanup `gsutil rm`. All `gcloud`/`gsutil` calls target `tan-nb-exp` per the repository
`CLAUDE.md`; never point them at another project.

VM lifecycle. If the VM was `TERMINATED`, M0 step 1 starts it; you may stop it again afterward
(`gcloud compute instances stop nagare-01 --zone=us-west1-a --project=tan-nb-exp`) — the `db-spike`
namespace and its data persist on the boot/data disks across a stop/start, so you can resume the spike
mid-way.

### Integration Point IP2 — the verified per-engine rendered shapes

These are the exact manifest shapes EP-44's renderer (`cli/nagare-dsl/src/Nagare/Dsl/Database/Render.hs`)

```yaml

  name: <name>
  namespace: <namespace>

  name: <name>
  namespace: <namespace>

    nagare.dev/managed-by: nagarectl

  type: ClusterIP
```

### Integration Point IP3 — the managed credential Secret contract

The Secret is named **`nagare-db-<name>`**, carries the labels `nagare.dev/managed-by: nagarectl`,
`nagare.dev/database: <name>`, `nagare.dev/engine: <engine>`, and holds engine-specific keys. **The renderer
(EP-44) emits the Secret's name/labels and the StatefulSet's `envFrom`/`secretKeyRef` wiring; the *values*
are generated by `nagarectl db create` (EP-45) at create time and never appear in `Config.hs`.** During the
spike the values were a fixed throwaway password (`spikepw12345`) hand-written into the Secret purely to
verify each engine reads the keys. Verified per-engine keys:

```yaml
# Postgres — nagare-db-<name>
POSTGRES_USER:     <user>            # e.g. appuser
POSTGRES_PASSWORD: <generated>       # by EP-45; never in Config.hs
POSTGRES_DB:       <db>              # e.g. appdb
DATABASE_URL:      postgresql://<user>:<generated>@<name>.<namespace>.svc.cluster.local:5432/<db>

# Redis — nagare-db-<name>
REDIS_PASSWORD:    <generated>
REDIS_URL:         redis://:<generated>@<name>.<namespace>.svc.cluster.local:6379

# ClickHouse — nagare-db-<name>
CLICKHOUSE_USER:     <user>
CLICKHOUSE_PASSWORD: <generated>
CLICKHOUSE_URL:      clickhouse://<user>:<generated>@<name>.<namespace>.svc.cluster.local:9000
```

The spike verified that each engine honors its password from these keys: Postgres and ClickHouse read
`*_USER`/`*_PASSWORD`/`*_DB` directly from the container env (`envFrom: secretRef`); Redis required the
password to be interpolated into `--requirepass "$REDIS_PASSWORD"` because the `redis:7` image does not read
a password env var on its own. EP-46 (app env injection) and EP-47 (backup/restore) read this Secret by
name/label and must never re-derive credentials. The URLs and `*_PASSWORD` keys, when injected into an app,
render as `valueFrom.secretKeyRef` (they embed the password); host/port/user/db render as inline literals
(IP5, EP-46).

### Substrate and behavior facts (settled by the spike, consumed by EP-44/EP-45/EP-47)

The substrate is a single-replica **StatefulSet** (confirmed in M1–M3): stable pod name `<name>-0`, stable
ClusterIP DNS `<name>.<namespace>.svc.cluster.local`, never public. The data PVC is a **standalone PVC**
reusing the `local-path`/RWO/`nagare-db-<name>-data` convention (NOT a `volumeClaimTemplates` entry), so it
is discoverable by `nagarectl storage` and independently retainable per `RetentionPolicy`. A **pod restart
re-mounts the same PVC and data persists** for all three engines — the central durability finding (M1/M2/M3
step 3). Single-writer note: because each database is one replica, there is no concurrent-writer hazard like
EP-33's Knative create-before-delete overlap; a StatefulSet with `replicas: 1` deletes-before-recreates, so
EP-44/EP-45 should prefer the default `RollingUpdate` (or `OnDelete`) update strategy and never run two
replicas. **ClickHouse viability** on `e2-standard-2` requires the container memory limit and the
`max_server_memory_usage` cap from M3; the exact working numbers are fixed in M4 and are a hard input to
EP-44's ClickHouse rendering and EP-45's default sizing.
