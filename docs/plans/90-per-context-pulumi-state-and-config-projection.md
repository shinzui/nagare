## Purpose / Big Picture

Today nagare's cloud infrastructure (the GCP VM, static IP, Cloud DNS zone, disks,
service account, Artifact Registry, and backup bucket) is provisioned by a **Pulumi**
program in `infra/pulumi/`. **Pulumi** is an infrastructure-as-code tool: a program
(here TypeScript, `infra/pulumi/index.ts`) describes the desired cloud resources, and
`pulumi up` reconciles the real cloud to match. Pulumi keeps two pieces of bookkeeping:

- **State** — a JSON ledger of every resource Pulumi has created and its current
  attributes, so the next `pulumi up` knows what already exists. nagare keeps this state
  in a **file backend**: a directory on disk that Pulumi reads and writes, selected today
  by the comment-documented `pulumi login file://./infra/pulumi/.pulumi-state` and the
  `PULUMI_HOME="$PWD/infra/pulumi/.pulumi-home"` export in the repo-root `.envrc`. There
  is exactly **one** state tree and exactly **one stack** named `dev` (a *stack* is one
  named instance of the program's resources).
- **Config** — the per-stack input values, stored in `infra/pulumi/Pulumi.dev.yaml`.
  This file is **tracked in git** and **pins one project**: `gcp:project: tan-nb-exp`,
  `gcp:region: us-west1`, `gcp:zone: us-west1-a`, `nagare:imageBucket:
  tan-nb-exp-nagare-images`, and a `nagare:nagareImageSelfLink` that embeds
  `tan-nb-exp`. Because state is keyed off `$PWD` and the config is a tracked,
  project-specific file, **one working directory == one Pulumi target**: a second GCP
  project means a second checkout, and the tracked `Pulumi.dev.yaml` forces a file edit
  to point anywhere but `tan-nb-exp`.

This is the Pulumi half of MasterPlan 17's goal — *first-class, named target contexts*,
where an operator defines many named targets (each a full bundle of project / region /
buckets / domain) in a user-level store and selects one per command, exactly like
`kubectl --context`. The MasterPlan is
`docs/masterplans/17-first-class-target-contexts-for-nagare.md`; this plan implements its
**Integration Point 5** ("Per-context Pulumi state and config projection").

The chosen model is **stack-per-context, plus a per-context file backend** (MasterPlan 17
Integration Point 5, and the Decision Log below). Concretely:

- **A context maps to a Pulumi stack: the stack name *is* the context name.** So context
  `labs` is Pulumi stack `labs`, and its config lives in `infra/pulumi/Pulumi.labs.yaml`;
  context `tan-nb-exp` is stack `tan-nb-exp` with `infra/pulumi/Pulumi.tan-nb-exp.yaml`.
  The per-stack config files coexist in the project directory, so switching contexts never
  overwrites another context's config. `pulumi -C infra/pulumi stack ls` then **reads as
  the context list** — one row per context.
- **Each context is additionally backed by its own file backend directory** for hard,
  filesystem-level state isolation:
  `file://${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<context>/state`, with a matching
  per-context `PULUMI_HOME=${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<context>/home`.
  Two contexts therefore never share a state tree even on disk.

After this change:

- **Each context owns an isolated Pulumi stack and state tree.** Selecting context `labs`
  and running `pulumi up` reconciles `labs`'s resources against stack `labs` in `labs`'s
  own backend; selecting `tan-nb-exp` touches only stack `tan-nb-exp` in its backend. You
  can see it by running `nagarectl context use labs`, then
  `pulumi -C infra/pulumi stack ls`, and observing the selected stack is `labs` with its
  own resource count, distinct from what `tan-nb-exp` shows.
- **`infra/pulumi/Pulumi.dev.yaml` is no longer tracked and no longer pins `tan-nb-exp`.**
  Each context's `Pulumi.<context>.yaml` is a **per-context projection** — a generated
  file derived from that context's bundle — regenerated by `nagarectl init` and
  `nagarectl context use`. A fresh clone carries no `tan-nb-exp` Pulumi config; you create
  `Pulumi.<yourcontext>.yaml` for *your* context by initialising one. You can see it by
  running `git ls-files infra/pulumi/` (no `Pulumi.*.yaml` stack config listed) and by
  `git grep tan-nb-exp -- infra/pulumi/` returning nothing tracked.
- **The `nagareImageSelfLink` flow keeps working, per context.** `scripts/upload-images.sh`
  still writes the registered NixOS image's self-link into the *active context's stack*
  config (`Pulumi.<context>.yaml`), and switching contexts uses that context's own
  self-link — never another project's. Because each context is a separate stack config
  file, this persists naturally.

The behavior a human verifies at the end: two contexts, two `pulumi stack ls` rows (one
per context) with two independent state trees and two independent `Pulumi.<context>.yaml`
projections, and zero tracked `tan-nb-exp` Pulumi config in the repository.

## Surprises & Discoveries

Document unexpected behaviors, bugs, optimizations, or insights discovered during
implementation. Provide concise evidence.

- (M0, expected) `pulumi` reads the file backend from `PULUMI_BACKEND_URL` when set,
  overriding any `pulumi login` recorded in `$PULUMI_HOME/credentials.json`. This is why the
  plan replaces the comment-documented `pulumi login file://./infra/pulumi/.pulumi-state` with
  an exported `PULUMI_BACKEND_URL` per context — no interactive `pulumi login` step is needed,
  and the selection is stateless (derived fresh from the context each shell). Record the
  confirming transcript here during M0.
- (M0, to confirm) The **selected stack** is remembered per `PULUMI_HOME` (Pulumi's workspace
  file). Because each context has its own `PULUMI_HOME`, selecting stack `<context>` once (on
  `context use`) means later bare `pulumi -C infra/pulumi stack output …` calls in that
  context resolve to the right stack without repeating `--stack`. Record whether this holds, or
  whether callers must pass `--stack "$NAGARE_PULUMI_STACK"` explicitly.
- (M0, confirmed) The installed Pulumi v3.239.0 honors `PULUMI_BACKEND_URL=file://<dir>` and writes
  stack config as `Pulumi.<stack>.yaml`; a stack selected in one process is remembered by the same
  `PULUMI_HOME` in a later process. Transcript:
  `stack init labs` created `Pulumi.labs.yaml`; `stack init tan-nb-exp` created
  `Pulumi.tan-nb-exp.yaml`; `stack --show-name` under the first home printed `labs`; separate
  `state/.pulumi` directories were created for the two homes.
- (M3) `pulumi stack init` from Haskell did not accept an empty
  `PULUMI_CONFIG_PASSPHRASE` reliably, even though the same empty export works from the shell. Using
  a zero-byte `PULUMI_CONFIG_PASSPHRASE_FILE` under the per-context Pulumi home keeps the same empty
  passphrase semantics and makes non-interactive stack initialization deterministic.

## Decision Log

Record every decision made while working on the plan.

- Decision: **Adopt stack-per-context plus a per-context file backend (Option B).** A context
  maps to a Pulumi stack whose name *is* the context name; each context additionally gets its
  own file backend directory (`file://${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<ctx>/state`)
  and a matching per-context `PULUMI_HOME`. `Pulumi.<ctx>.yaml` config files coexist in the
  project directory.
  Rationale: This gives **both** a legible `pulumi stack ls` (it reads as the context list, one
  row per context) **and** hard, filesystem-level isolation of each context's state tree and
  secrets. Because each context is a distinct stack config file, switching contexts never
  overwrites another context's config, and `nagareImageSelfLink` persists per context with no
  extra bookkeeping. This matches MasterPlan 17 Integration Point 5 as revised by the owner.
  Date: 2026-06-30

- Decision (REJECTED alternative): **relocate only the file backend per context, keeping a
  single stack `dev`** (the earlier draft of this plan). Under it, every context reused stack
  name `dev`, the backend directory alone differed per context, and the single stack-config file
  had to be swapped in per context (via a provisional `stackConfigDir` symlink) so that
  `pulumi config set` and `nagareImageSelfLink` did not clobber another context's config.
  Rationale for rejection: it produced a `pulumi stack ls` that showed only an anonymous `dev`
  (no context legibility), and it required the `stackConfigDir`/symlink swap machinery to keep
  per-context config from colliding. Stack-per-context removes that machinery entirely (distinct
  `Pulumi.<ctx>.yaml` files coexist) and makes `stack ls` self-describing, while the per-context
  backend still delivers the filesystem isolation the relocate-only scheme was reaching for. The
  `stackConfigDir` mechanism is therefore **not used**; it survives only as this footnote.
  Date: 2026-06-30

- Decision (REJECTED alternative): **one shared backend keyed only by stack** (all contexts'
  stacks in a single `file://` tree, or a shared remote/GCS backend).
  Rationale for rejection: it co-locates every context's state and secrets in one tree — weaker
  isolation than the owner wants — and MasterPlan 17 scope keeps the file backend rather than
  migrating to remote/GCS. A shared-backend, stack-per-context model remains a possible follow-on
  if cross-context visibility from a single backend is ever desired; for v1 the per-context
  backend is preferred for hard isolation.
  Date: 2026-06-30

- Decision: **Untrack `infra/pulumi/Pulumi.dev.yaml`** and replace it with per-context
  `Pulumi.<ctx>.yaml` **projections** regenerated from the active context's bundle by
  `nagarectl init` and `nagarectl context use`. Git-ignore `infra/pulumi/Pulumi.*.yaml`
  (which does not match the tracked project file `infra/pulumi/Pulumi.yaml`).
  Rationale: The tracked file is the last Pulumi-side hardcode of `tan-nb-exp` (MasterPlan 17
  Vision). A projection regenerated from the context means a second instance needs zero
  tracked-file edits, and the config can never drift from the context it belongs to. The
  `nagare:nagareImageSelfLink` value (written by `scripts/upload-images.sh`) is genuinely
  per-target and is preserved because each context is its own `Pulumi.<ctx>.yaml`.
  Date: 2026-06-30

- Decision: **Use `NAGARE_CONTEXT` as the resolved active-context-name variable** (the same
  name sibling `docs/plans/89-shell-and-direnv-context-resolution-and-the-context-aware-guardrail.md`
  exports from `scripts/lib/target.sh`/`.envrc`, and the same env var EP-87's precedence honours).
  Do not introduce a separate `NAGARE_ACTIVE_CONTEXT`.
  Rationale: One name across the Haskell resolver, bash resolution, and this plan avoids a
  cross-plan naming split. `Nagare.Target.pulumiEnvFor` keys off the resolved `NAGARE_CONTEXT`.
  Date: 2026-06-30

- Decision: **Use a zero-byte passphrase file for non-interactive CLI stack initialization**, while
  preserving the existing empty-passphrase provider contract. `scripts/lib/target.sh` and
  `nagarectl` create `${PULUMI_HOME}/passphrase` and export `PULUMI_CONFIG_PASSPHRASE_FILE` to it;
  `.envrc` still exports `PULUMI_CONFIG_PASSPHRASE=""` for the shell path.
  Rationale: Pulumi v3.239.0 accepted an empty passphrase env var from the shell, but the
  Haskell-launched `stack init` reported it as unset. The zero-byte file is explicit, works in both
  paths, and does not introduce a real secret.
  Date: 2026-07-01
