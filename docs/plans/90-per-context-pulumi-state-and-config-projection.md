# Per-context Pulumi state and config projection

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.


## Purpose / Big Picture

Today nagare's cloud infrastructure (the GCP VM, static IP, Cloud DNS zone, disks,
service account, Artifact Registry, and backup bucket) is provisioned by a **Pulumi**
program in `infra/pulumi/`. **Pulumi** is an infrastructure-as-code tool: a program
(here TypeScript, `infra/pulumi/index.ts`) describes the desired cloud resources, and
`pulumi up` reconciles the real cloud to match. Pulumi keeps two pieces of bookkeeping:

- **State** — a JSON ledger of every resource Pulumi has created and its current
  attributes, so the next `pulumi up` knows what already exists. nagare keeps this state
  in a **file backend**: a directory on disk that Pulumi reads and writes, selected today
  by the comment-documented `pulumi login file://./infra/pulumi/.pulumi-state` and the
  `PULUMI_HOME="$PWD/infra/pulumi/.pulumi-home"` export in the repo-root `.envrc`. There
  is exactly **one** state tree and exactly **one stack** named `dev` (a *stack* is one
  named instance of the program's resources).
- **Config** — the per-stack input values, stored in `infra/pulumi/Pulumi.dev.yaml`.
  This file is **tracked in git** and **pins one project**: `gcp:project: tan-nb-exp`,
  `gcp:region: us-west1`, `gcp:zone: us-west1-a`, `nagare:imageBucket:
  tan-nb-exp-nagare-images`, and a `nagare:nagareImageSelfLink` that embeds
  `tan-nb-exp`. Because state is keyed off `$PWD` and the config is a tracked,
  project-specific file, **one working directory == one Pulumi target**: a second GCP
  project means a second checkout, and the tracked `Pulumi.dev.yaml` forces a file edit
  to point anywhere but `tan-nb-exp`.

This is the Pulumi half of MasterPlan 17's goal — *first-class, named target contexts*,
where an operator defines many named targets (each a full bundle of project / region /
buckets / domain) in a user-level store and selects one per command, exactly like
`kubectl --context`. The MasterPlan is
`docs/masterplans/17-first-class-target-contexts-for-nagare.md`; this plan implements its
**Integration Point 5** ("Per-context Pulumi state and config projection").

The chosen model is **stack-per-context, plus a per-context file backend** (MasterPlan 17
Integration Point 5, and the Decision Log below). Concretely:

- **A context maps to a Pulumi stack: the stack name *is* the context name.** So context
  `labs` is Pulumi stack `labs`, and its config lives in `infra/pulumi/Pulumi.labs.yaml`;
  context `tan-nb-exp` is stack `tan-nb-exp` with `infra/pulumi/Pulumi.tan-nb-exp.yaml`.
  The per-stack config files coexist in the project directory, so switching contexts never
  overwrites another context's config. `pulumi -C infra/pulumi stack ls` then **reads as
  the context list** — one row per context.
- **Each context is additionally backed by its own file backend directory** for hard,
  filesystem-level state isolation:
  `file://${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<context>/state`, with a matching
  per-context `PULUMI_HOME=${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<context>/home`.
  Two contexts therefore never share a state tree even on disk.

After this change:

- **Each context owns an isolated Pulumi stack and state tree.** Selecting context `labs`
  and running `pulumi up` reconciles `labs`'s resources against stack `labs` in `labs`'s
  own backend; selecting `tan-nb-exp` touches only stack `tan-nb-exp` in its backend. You
  can see it by running `nagarectl context use labs`, then
  `pulumi -C infra/pulumi stack ls`, and observing the selected stack is `labs` with its
  own resource count, distinct from what `tan-nb-exp` shows.
- **`infra/pulumi/Pulumi.dev.yaml` is no longer tracked and no longer pins `tan-nb-exp`.**
  Each context's `Pulumi.<context>.yaml` is a **per-context projection** — a generated
  file derived from that context's bundle — regenerated by `nagarectl init` and
  `nagarectl context use`. A fresh clone carries no `tan-nb-exp` Pulumi config; you create
  `Pulumi.<yourcontext>.yaml` for *your* context by initialising one. You can see it by
  running `git ls-files infra/pulumi/` (no `Pulumi.*.yaml` stack config listed) and by
  `git grep tan-nb-exp -- infra/pulumi/` returning nothing tracked.
- **The `nagareImageSelfLink` flow keeps working, per context.** `scripts/upload-images.sh`
  still writes the registered NixOS image's self-link into the *active context's stack*
  config (`Pulumi.<context>.yaml`), and switching contexts uses that context's own
  self-link — never another project's. Because each context is a separate stack config
  file, this persists naturally.

The behavior a human verifies at the end: two contexts, two `pulumi stack ls` rows (one
per context) with two independent state trees and two independent `Pulumi.<context>.yaml`
projections, and zero tracked `tan-nb-exp` Pulumi config in the repository.

## Decision Log

Record every decision made while working on the plan.

- Decision: **Adopt stack-per-context plus a per-context file backend (Option B).** A context
  maps to a Pulumi stack whose name *is* the context name; each context additionally gets its
  own file backend directory (`file://${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<ctx>/state`)
  and a matching per-context `PULUMI_HOME`. `Pulumi.<ctx>.yaml` config files coexist in the
  project directory.
  Rationale: This gives **both** a legible `pulumi stack ls` (it reads as the context list, one
  row per context) **and** hard, filesystem-level isolation of each context's state tree and
  secrets. Because each context is a distinct stack config file, switching contexts never
  overwrites another context's config, and `nagareImageSelfLink` persists per context with no
  extra bookkeeping. This matches MasterPlan 17 Integration Point 5 as revised by the owner.
  Date: 2026-06-30

- Decision (REJECTED alternative): **relocate only the file backend per context, keeping a
  single stack `dev`** (the earlier draft of this plan). Under it, every context reused stack
  name `dev`, the backend directory alone differed per context, and the single stack-config file
  had to be swapped in per context (via a provisional `stackConfigDir` symlink) so that
  `pulumi config set` and `nagareImageSelfLink` did not clobber another context's config.
  Rationale for rejection: it produced a `pulumi stack ls` that showed only an anonymous `dev`
  (no context legibility), and it required the `stackConfigDir`/symlink swap machinery to keep
  per-context config from colliding. Stack-per-context removes that machinery entirely (distinct
  `Pulumi.<ctx>.yaml` files coexist) and makes `stack ls` self-describing, while the per-context
  backend still delivers the filesystem isolation the relocate-only scheme was reaching for. The
  `stackConfigDir` mechanism is therefore **not used**; it survives only as this footnote.
  Date: 2026-06-30

- Decision (REJECTED alternative): **one shared backend keyed only by stack** (all contexts'
  stacks in a single `file://` tree, or a shared remote/GCS backend).
  Rationale for rejection: it co-locates every context's state and secrets in one tree — weaker
  isolation than the owner wants — and MasterPlan 17 scope keeps the file backend rather than
  migrating to remote/GCS. A shared-backend, stack-per-context model remains a possible follow-on
  if cross-context visibility from a single backend is ever desired; for v1 the per-context
  backend is preferred for hard isolation.
  Date: 2026-06-30

- Decision: **Untrack `infra/pulumi/Pulumi.dev.yaml`** and replace it with per-context
  `Pulumi.<ctx>.yaml` **projections** regenerated from the active context's bundle by
  `nagarectl init` and `nagarectl context use`. Git-ignore `infra/pulumi/Pulumi.*.yaml`
  (which does not match the tracked project file `infra/pulumi/Pulumi.yaml`).
  Rationale: The tracked file is the last Pulumi-side hardcode of `tan-nb-exp` (MasterPlan 17
  Vision). A projection regenerated from the context means a second instance needs zero
  tracked-file edits, and the config can never drift from the context it belongs to. The
  `nagare:nagareImageSelfLink` value (written by `scripts/upload-images.sh`) is genuinely
  per-target and is preserved because each context is its own `Pulumi.<ctx>.yaml`.
  Date: 2026-06-30

- Decision: **Use `NAGARE_CONTEXT` as the resolved active-context-name variable** (the same
  name sibling `docs/plans/89-shell-and-direnv-context-resolution-and-the-context-aware-guardrail.md`
  exports from `scripts/lib/target.sh`/`.envrc`, and the same env var EP-87's precedence honours).
  Do not introduce a separate `NAGARE_ACTIVE_CONTEXT`.
  Rationale: One name across the Haskell resolver, bash resolution, and this plan avoids a
  cross-plan naming split. `Nagare.Target.pulumiEnvFor` keys off the resolved `NAGARE_CONTEXT`.
  Date: 2026-06-30

## Context and Orientation

This section assumes no prior knowledge of the repository.

**What a "context" is (defined by EP-87).** A *context* is a named, fully-resolved deploy
target: a bundle of `project, region, zone, registryHost, artifactRegistryId, imageBucket,
backupBucket, baseDomain, instanceName, targetPlatform, mode, localObjectStore` plus its
Pulumi-state location. EP-87 — `docs/plans/87-target-context-model-store-and-resolver-for-nagarectl.md`
(a **hard dependency** of this plan) — owns the context model, the user-level store
(`${XDG_CONFIG_HOME:-$HOME/.config}/nagare/contexts/<name>.env`, each file a flat list of
`export VAR=value` lines), the `current-context` pointer
(`${XDG_CONFIG_HOME:-$HOME/.config}/nagare/current-context`), and the resolution precedence
(`--context`/`NAGARE_CONTEXT` > pointer > in-repo `nagare.target.env`/`nagare.local.env` >
built-in `tan-nb-exp` default). This plan does **not** define the context model; it consumes
it and defines the *Pulumi-state location + stack-naming* part of it. In Haskell the bundle is
the record `Nagare.Target.TargetProfile` (in `cli/nagarectl/src/Nagare/Target.hs`); EP-87
extends it with the active context name. Where this plan needs "the active context name", it is
the value of `NAGARE_CONTEXT` as EP-87/EP-89 resolve it; for a back-compat in-repo profile with
no named context, this plan uses the synthetic name **`default`** (see M1).

**Where Pulumi is configured today.** Four files matter:

- `infra/pulumi/Pulumi.yaml` — the project file: `name: nagare`, `runtime: nodejs`. Tracked,
  project-wide (not per-stack). This plan does **not** need to edit it (Option B needs no
  `stackConfigDir`).
- `infra/pulumi/Pulumi.dev.yaml` — the **stack** config for stack `dev`. **Tracked**, and the
  hardcode this plan removes. Its current contents:

  ```yaml
  encryptionsalt: v1:lZdyzLa0QaQ=:v1:BlCRz+tX+iTBc9FC:yTuViqunFExom4euMWPn/bVOlg20MA==
  config:
    gcp:project: tan-nb-exp
    gcp:region: us-west1
    gcp:zone: us-west1-a
    nagare:baseDomain: apps.example.com
    nagare:imageBucket: tan-nb-exp-nagare-images
    nagare:nagareImageSelfLink: https://www.googleapis.com/compute/v1/projects/tan-nb-exp/global/images/nagare-image-gnq7zw6pwd1a
  ```

- `infra/pulumi/index.ts` — the program. It is **already config-driven**: it reads
  `gcpCfg.require("project")`, `gcpCfg.require("region")`, `gcpCfg.require("zone")`,
  `cfg.require("imageBucket")`, `cfg.get("instanceName") ?? "nagare-01"`,
  `cfg.get("baseDomain") ?? "apps.example.com"`, `cfg.get("nagareImageSelfLink")`, etc. The
  problem this plan fixes is **not** the program — it is *where that config lives* (a tracked,
  pinned single file) and *that state/stack is single and $PWD-bound*.
- `.envrc` (repo root) — sets `PULUMI_HOME="$PWD/infra/pulumi/.pulumi-home"` and
  `PULUMI_CONFIG_PASSPHRASE=""`, and documents the backend in a comment as
  `pulumi login file://./infra/pulumi/.pulumi-state` (which "resolves relative to
  infra/pulumi/"). So today the state directory is `infra/pulumi/.pulumi-state` and the home
  is `infra/pulumi/.pulumi-home`, both already git-ignored (`.gitignore` lines 27–28).

**Who reads/writes Pulumi config and state (the callers this plan must keep correct).**

- `cli/nagarectl/src/Nagare/Init.hs` — `seedPulumiConfig :: Bool -> TargetProfile -> IO (Either (Text, ExitCode) ())`
  runs `pulumi -C infra/pulumi config set KEY VALUE` for the eight keys in `seedKeys`
  (`gcp:project`, `gcp:region`, `gcp:zone`, `nagare:baseDomain`, `nagare:imageBucket`,
  `nagare:backupBucket`, `nagare:artifactRegistryId`, `nagare:instanceName`). The argv is
  built by the pure `pulumiConfigSetArgs key value = ["-C", "infra/pulumi", "config", "set", …]`.
  `seedPulumiConfig` is called by `runInit` (wired in `cli/nagarectl/app/Main.hs`, command
  `Init`). **Under Option B this must target the active stack** — see M2/M3 (`--stack <ctx>` or
  a prior `stack select`).
- `scripts/upload-images.sh` — `pulumi --cwd infra/pulumi config get imageBucket` to find the
  GCS image bucket, and at the end `pulumi --cwd infra/pulumi config set nagareImageSelfLink
  <self-link>` to record the registered image. The self-link embeds the project, so it is
  per-target and must never be committed for a foreign project.
- `cli/nagarectl/src/Nagare/Ops/Pulumi.hs` — `stackOutput :: FilePath -> Text -> IO (Maybe Text)`
  runs `pulumi -C <dir> stack output <name>`; callers pass `dir = "infra/pulumi"` (the
  `ioPulumiDir` default in `cli/nagarectl/src/Nagare/Ops/Status.hs`). It reads `publicIp`,
  `baseDomain`, `backupBucket`.
- `cli/nagarectl/src/Nagare/Ops/Doctor.hs` — embeds `pulumi -C infra/pulumi stack output …`
  inside *printed remediation strings* (not executed), so it needs only doc-text updates if at
  all.
- `justfile` — `infra-up` / `infra-preview` (`cd infra/pulumi && pulumi up|preview`) and
  `cluster-bootstrap` (`BASE_DOMAIN="$(pulumi -C infra/pulumi stack output baseDomain)"`).
- `scripts/live-smoke.sh` — `cd "${NAGARE_REPO_ROOT}/infra/pulumi" && pulumi stack output publicIp`.

The crucial property all of these share: **none names the backend on the command line, and
none names the stack beyond the currently-selected one.** They rely on the *ambient*
`PULUMI_HOME` (which, per context, also records the *selected stack*). That is what makes the
per-context relocation low-blast-radius: repoint the ambient `PULUMI_HOME`/`PULUMI_BACKEND_URL`
and select stack `<context>` per context, and every caller follows along **without a signature
change** — except the one case where the *resolved* context differs from the *ambient shell*
context (`nagarectl --context labs …`), which this plan handles in M3 by having nagarectl set
the Pulumi environment and select the stack from the resolved context before it shells out.

**Term definitions used below.** *Projection*: a generated file derived from the context bundle
(not hand-edited, not tracked). *Backend*: the directory Pulumi stores state in. *Stack*: a named
instance of the program's resources; here the stack name equals the context name. *XDG state
home*: `${XDG_STATE_HOME:-$HOME/.local/state}`, the conventional location for state that is not
config and not cache.


## Plan of Work

The work is five milestones. M0 is a short prototype that de-risks the stack-per-context +
per-context-backend mechanism. M1 relocates state and creates/selects the per-context stack. M2
untracks and projects the config. M3 wires the callers and proves isolation. M4 migrates existing
in-repo state and documents recovery. M1–M3 are the substance; M0 confirms the mechanism; M4 is
the safety net.

### The path + naming scheme (used by every milestone)

Given an active context name `<ctx>` (e.g. `tan-nb-exp`, `labs`, or the synthetic `default`),
this plan defines one root and two children, plus the stack name and the config file:

```text
ROOT = ${XDG_STATE_HOME:-$HOME/.local/state}/nagare/<ctx>
  ROOT/state   -> the file backend   => PULUMI_BACKEND_URL=file://ROOT/state
  ROOT/home    -> the Pulumi home     => PULUMI_HOME=ROOT/home
stack name     = <ctx>                => pulumi stack select <ctx>  (init if absent)
stack config   = infra/pulumi/Pulumi.<ctx>.yaml   (git-ignored per-context projection)
```

The stack config `Pulumi.<ctx>.yaml` lives in the project directory (Pulumi's default location),
so no `stackConfigDir` relocation is needed and distinct contexts' configs coexist. State and the
Pulumi home go under `XDG_STATE_HOME` (machine state, regenerable/recoverable), not
`XDG_CONFIG_HOME` (where EP-87 keeps the operator's source-of-truth context *definitions*).

### M0 — Prototype the stack-per-context mechanism (de-risk before wiring)

**Scope.** Confirm three facts about the installed `pulumi` (v3.239.0, verified via
`pulumi version`): (1) `PULUMI_BACKEND_URL=file://<dir>` selects that file backend without an
interactive `pulumi login`; (2) `pulumi stack init <name>` / `stack select <name>` create and
select a stack named after the context and write `Pulumi.<name>.yaml` in the project dir; (3) the
selected stack persists in the per-context `PULUMI_HOME` workspace, so a later bare
`pulumi stack output` resolves to it.

**Work.** In a scratch dir, create a throwaway Pulumi project, export `PULUMI_BACKEND_URL`,
`PULUMI_HOME`, and `PULUMI_CONFIG_PASSPHRASE=""`, run `pulumi stack init labs`,
`pulumi config set foo bar`, and observe `Pulumi.labs.yaml` appear. Repeat with a second
context name and confirm both `Pulumi.<ctx>.yaml` coexist and `pulumi stack ls` lists the
selected stack. Point `PULUMI_HOME`/`PULUMI_BACKEND_URL` at a second directory and confirm state
isolation.

**Result.** A recorded transcript in Surprises & Discoveries, and confirmation of whether the
selected stack persists per `PULUMI_HOME` (deciding whether callers may rely on ambient selection
or must pass `--stack "$NAGARE_PULUMI_STACK"`). Nothing in the real `infra/pulumi/` is modified.

**Acceptance.** The prototype shows two coexisting `Pulumi.<ctx>.yaml`, two isolated state trees,
and a `stack ls` naming the selected stack; the persistence question is answered in the Decision
Log / Surprises.

### M1 — Per-context Pulumi state + stack

**Scope.** Make the file backend, `PULUMI_HOME`, and the *selected stack* per-context. At the end,
entering the repo with context `labs` active yields
`PULUMI_BACKEND_URL=file://…/nagare/labs/state`, `PULUMI_HOME=…/nagare/labs/home`, and stack
`labs` selected; with `tan-nb-exp` active, the `tan-nb-exp` paths and stack. No state is shared.

**Work.**

1. Add a dependency-free bash helper mapping a context name to the paths + stack and exporting
   the environment. Its home is a new function in `scripts/lib/target.sh` (the file EP-89 already
   extends to resolve the active context) — e.g. `_export_pulumi_env`:

   ```bash
   # Derive the per-context Pulumi backend/home/stack from the active context name.
   # NAGARE_CONTEXT is resolved+exported by EP-89's context resolution; default to
   # "default" for a back-compat in-repo profile with no named context.
   _export_pulumi_env() {
     local ctx="${NAGARE_CONTEXT:-default}"
     local state_home="${XDG_STATE_HOME:-$HOME/.local/state}"
     local root="${state_home}/nagare/${ctx}"
     mkdir -p "${root}/state" "${root}/home"
     export PULUMI_HOME="${root}/home"
     export PULUMI_BACKEND_URL="file://${root}/state"
     export NAGARE_PULUMI_STACK="${ctx}"   # = stack name; callers may pass --stack "$NAGARE_PULUMI_STACK"
     # Ensure the stack exists and is selected in this per-context PULUMI_HOME.
     # (Stack selection persists in PULUMI_HOME so later bare `pulumi` calls resolve it.)
     local pd="${NAGARE_REPO_ROOT:-$PWD}/infra/pulumi"
     pulumi -C "${pd}" stack select "${ctx}" 2>/dev/null \
       || pulumi -C "${pd}" stack init "${ctx}" 2>/dev/null || true
   }
   ```

   The `stack select … || stack init …` is guarded with `|| true` so a shell can be entered even
   before `pulumi` is on `PATH` (the flake devShell provides it); it becomes effective once the
   toolchain is loaded. The `2>/dev/null` avoids noise when the stack already exists.

2. In `.envrc` (repo root), **replace** the two Pulumi lines
   (`export PULUMI_HOME="$PWD/infra/pulumi/.pulumi-home"` and the
   `pulumi login file://./infra/pulumi/.pulumi-state` comment) with a call into the same helper,

## Idempotence and Recovery

**Idempotence.** Every step is safe to repeat:

- `_export_pulumi_env` only `mkdir -p`s, re-exports, and `stack select … || stack init …`
  (selecting an existing stack is a no-op; init of an existing stack fails harmlessly under
  `|| true`). Re-running it is a no-op.
- **Regenerating the projection is safe.** `seedPulumiConfig` runs `pulumi config set` for fixed
  keys to fixed values derived from the context; running it twice yields the same
  `Pulumi.<ctx>.yaml`. It never touches `nagareImageSelfLink`, so re-seeding never clobbers a
  self-link written by `upload-images.sh`. Because each context is a separate stack config file,
  re-seeding one context cannot affect another.
- `git rm --cached` + the `.gitignore` append are idempotent (a second `git rm --cached` is a
  harmless error; a duplicate `.gitignore` line is inert). The M4 migration uses `cp -an`/`cp -n`
  (no-clobber) and a guarded `stack rename`, so re-running it never overwrites already-migrated
  state or double-renames.

**Recovery.**

- **Lost or corrupted projection.** Delete `infra/pulumi/Pulumi.<ctx>.yaml` and re-run
  `nagarectl init` (or `nagarectl context use <ctx>`); `seedPulumiConfig` rebuilds the eight keys
  from the context. Re-run `scripts/upload-images.sh` to restore `nagareImageSelfLink` (it
  re-derives the self-link from the registered GCE image; the script is idempotent and reuses
  existing images).
- **Lost stack / state tree.** The file backend under `…/nagare/<ctx>/state` is the only copy of a
  context's state. If it is deleted but the cloud resources still exist, recover by re-creating the
  stack (`pulumi -C infra/pulumi stack init <ctx>` against the context's backend) and running
  `pulumi -C infra/pulumi refresh` to repopulate state from the live cloud, or `pulumi import` for
  resources refresh cannot adopt. **Back up `…/nagare/<ctx>/state` before destructive operations**;
  it is a plain directory and can be `cp -a`'d. (This mirrors the pre-existing risk of the single
  in-repo `.pulumi-state`; the per-context relocation moves the directory, it does not add risk.)
- **Migration went wrong (M4).** The migration only *copies* (never moves) the in-repo state, so
  the original `infra/pulumi/.pulumi-state` remains until you delete it. If the per-context copy is
  bad, delete `…/nagare/<ctx>/state` and re-copy from the still-present in-repo directory. The
  `stack rename` is reversible with a second `stack rename` back to `dev`.
- **EP-89 not yet merged.** The M1 fallback resolution (read `NAGARE_CONTEXT`, else
  `current-context`, else `default`) keeps this plan independently verifiable; when EP-89's resolver
  lands and exports `NAGARE_CONTEXT`, delete the fallback and note it in the Decision Log.
