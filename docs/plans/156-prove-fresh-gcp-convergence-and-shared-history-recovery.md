## Purpose / Big Picture

After this plan, an operator can create a fresh, production-shaped Nagare context in a GCP project and, once the safe-use gate passes, use it for low-risk work: the installed release candidate converges the cloud foundation, a NixOS virtual machine running k3s, the cluster platform and applications through reviewed public `nagarectl` commands, with inventory history stored in the context's GCS state bucket. On that context the plan proves the six operational checks the safe-use gate needs — an application change that leaves other owners untouched plus an unchanged replay, a GCS backup restored into an isolated target with checked content, recovery of an interrupted operation, recovery from a clean operator root, refusal of a second writer followed by explicit takeover, and exact cleanup including reviewed cloud teardown — together with automatic registry-credential refresh (F15) and native Google CDN. It writes redacted cloud evidence that the release gate ([EP-157](157-gate-the-inventory-release-on-complete-immutable-evidence.md)) accepts for the final candidate.

To see it working: on the fresh context, the GCP runner writes `target.json`, `fixture.json`, `cloud-health.json` and `inventory-evidence.json`, `scripts/assemble-inventory-release-index.py` accepts them for the candidate revision, and an independent reviewer has executed [the operations runbook](../runbooks/inventory-operations.md) end to end on the same context. **No GKE: this plan never creates, selects, authenticates to or depends on a GKE cluster.** Completing it does not make Nagare production-ready; MP-23's data-protection gate and MP-21's upgrade gate are separate.

## Surprises & Discoveries

Condensed in-force findings; dated detail is in [the snapshot](https://github.com/shinzui/nagare/blob/0c00498fcc3a332b724c0d0bb767d86c37ce21be/docs/audits/mp23-archive/plan-history/ep156-before-consolidation-2026-10-02.md).

Ambient workstation values leak into planning: active `labs` variables once made a disposable review name standing buckets, domain and VM. Plan in a clean environment (`env -i` with only `HOME`, `PATH`, the isolated XDG roots and the exact project), and have the runner assert every physical name in a saved review before apply.

Pulumi saved plans are stack-wide snapshots even with `--target`, so all new Pulumi resources of one scope form one inventory operation with one saved plan. A same-URN replacement between review and apply is not prevented by Pulumi's saved delete constraints, which bind the URN and operation class rather than the physical ID (F33); preflight and pre-execution rechecks narrow but do not eliminate this race against arbitrary external writers.

The Nix daemon does not inherit the caller's SSH `ProxyCommand`, and the GCE image derivation needs the `kvm` system feature; `scripts/upload-images.sh` opens a daemon-accessible pinned tunnel and the builder advertises `kvm`.

Project-list omission cannot prove a globally named GCS bucket absent, and a missing format object is not proof of an empty prefix. Store discovery distinguishes bound history, proved absence, foreign ownership, incomplete history and unavailable state, and treats a failed or slow read as unavailable, never as absence. Intermittent project-number lookup refusals stop planning before effects.

Real Knative graphs differ from recordings: a minimum-scale Pod keeps a 300-second termination grace, Events appear under two APIs with identical UIDs, and an uninventoried ownerless Endpoints can disappear with a reviewed descendant. The collection contract protects inventoried objects and assumes trusted controllers; it does not promise an atomic namespace UID set. Reproduce each native mismatch in the production-path interpreter fixtures (`just test-inventory-effects`) before another installed attempt.

Compute Engine metadata caches an access token until five minutes before expiry, so a 30-minute refresh timer that accepts any lifetime above 300 seconds can install a credential that expires before its next run (F31, [evidence](https://github.com/shinzui/nagare/blob/0c00498fcc3a332b724c0d0bb767d86c37ce21be/docs/audits/mp23-independent-results-2026-10-02/registry-timer-expiry-gap-f31.json)). Image cleanup that lists only ordinary containers misses sandbox (pause) images in use (F32, [evidence](https://github.com/shinzui/nagare/blob/0c00498fcc3a332b724c0d0bb767d86c37ce21be/docs/audits/mp23-independent-results-2026-10-02/image-prune-sandbox-f32.json)).

F30 was first observed and remains interrupted on the local `nagare-mp23-cp3` store ([handoff](https://github.com/shinzui/nagare/blob/0c00498fcc3a332b724c0d0bb767d86c37ce21be/docs/audits/mp23-independent-results-2026-10-02/application-status-race-f30-handoff.json)), (its Service UID matches the local F30 record), so A4's supported resume runs against that local store; the cloud consequence of F30 is covered by the C3 application-change check.
