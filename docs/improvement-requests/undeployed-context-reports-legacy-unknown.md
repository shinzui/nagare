# Improvement Request: a "not yet deployed" platform state and a re-pin for it

**Authored by:** a `claude-code` session implementing the `tan-ng-labs` rollout
(`mori://tan/tan-infrastructure`, `docs/plans/2026-06-30-nagare-labs-domain-delegation.md`; the
artifact-level plan URI is pending).
**Addressed to:** `shinzui/nagare` agents.
**Status:** accepted for implementation by
[ExecPlan 135](../plans/135-make-fresh-gcp-contexts-preflight-and-re-pin-cleanly.md).
**Created:** 2026-09-14.


## Why

The `labs` context was created with `nagarectl init` on `v0.2.1`. Because `v0.2.1` could not render a
host flake (IR-13), the operator moved to `v0.2.2` before creating any host or cluster. Then
`nagarectl platform status` printed:

```text
Nagare platform status (context labs)
CLI:        0.2.2
Payload:    0.2.2
Context:    0.2.1
Host:       legacy / unknown
Cluster:    legacy / unknown
Compatibility: legacy-unknown
```

Nothing here is legacy. The context is one patch behind, and the host and cluster simply do not
exist yet. The documented meaning of `legacy-unknown` is "at least one identity is absent, old, or
unreachable; inspect it before adoption or upgrade" (`docs/user/upgrades.md`, compatibility table),
which sends the operator looking for a problem that is not there, next to a
`platform mutation allowed (legacy-unknown)` guard line. The real signal, a patch skew between the
context pin and the release in use, is hidden.


## What is missing

- `assessPlatformStatus` compares the CLI, context, host and cluster identities with the payload, and
  any `LegacyUnknown` outranks `PatchSkew` in the aggregate
  (`cli/nagarectl/src/Nagare/Platform/Status.hs:99-112` at `v0.2.2`). An identity with no version is
  always `LegacyUnknown` (`cli/nagarectl/src/Nagare/Version.hs:93`), whether it is a genuinely
  pre-release object or one that has never been created. The status renderer prints both cases as
  `legacy / unknown` (`Status.hs:153`).
- The pin cannot be moved for a never-deployed context. `platform adopt` refuses any context that
  already has a version ("the selected context already has a platform version; use
  `nagarectl platform upgrade`", `Status.hs:175-178`). The upgrade flow's phases include a host
  switch and a Kubernetes apply, which make no sense with no host. `docs/user/upgrades.md` covers
  adopting a legacy context (`## Adopt a legacy context`, line 53) and upgrading a deployed one, but
  not re-pinning a context that was only initialised.
- The context therefore keeps `NAGARE_PLATFORM_VERSION=0.2.1` while every later operation runs from
  `0.2.2`, and the host flake generated by `0.2.2` records `0.2.2`, so the machine definition starts
  out internally inconsistent.


## Requested change

- Tell "not deployed yet" apart from "legacy or unreachable". For example, when the host has no
  instance in the context's project and the cluster is unreachable because it has never been
  bootstrapped, report those identities as `not deployed`, and base the aggregate on the remaining
  identities (here, `patch-skew`). If that cannot be detected reliably, at least give the absent-host
  and absent-cluster case its own wording in `platform status`.
- Provide a supported re-pin for an undeployed context, such as `nagarectl platform adopt` accepting
  a pinned context when neither a host nor a cluster exists, or a `platform upgrade` that skips
  host and Kubernetes phases which have nothing to act on. It should refuse as soon as a host or
  cluster identity is observed.
- Document it in `docs/user/upgrades.md` next to the adoption section.


## Required verification

- `PlatformSpec` cases: a patch-behind context with an absent host and cluster aggregates to the new
  state (or `patch-skew`), not `LegacyUnknown`; a context with a real but unversioned host still
  reports `LegacyUnknown`.
- A test that the re-pin refuses once a host or cluster identity exists.


## Acceptance

After moving a never-deployed context to the next patch release, `platform status` does not say
`legacy-unknown`, and one documented command brings the context pin level with the release in use.


## Non-goals

Changing how genuinely legacy (pre-pin) contexts are adopted, or relaxing the upgrade workflow for
deployed clusters.
