# db-spike — managed-database substrate reference manifests (EP-43)

House-style reference only — **not wired into anything**. These are the exact
raw-Kubernetes shapes the EP-43 feasibility spike applied by hand on the live
single-node k3s cluster to prove that PostgreSQL, Redis, and ClickHouse each run
as a single-replica **StatefulSet** with a standalone `local-path` PVC, a
ClusterIP Service for stable in-cluster DNS, and credentials sourced from a
managed Secret. They are the verified input shapes for the typed renderer EP-44
builds (`cli/nagare-dsl/src/Nagare/Dsl/Database/Render.hs`); see
`docs/plans/43-managed-database-substrate-spike-and-stateful-rendering-feasibility.md`
(Integration Points IP2/IP3) for the full contract and the captured evidence.

Each manifest carries a fixed throwaway password (`spikepw12345`) hand-written
into the Secret purely to verify each engine reads its credential keys. In the
real platform the password is generated by `nagarectl db create` (EP-45) and
never appears in config.

## What the spike proved (2026-06-10)

| Engine     | Image → version                          | Restart-survival | Backup command (local artifact)                          |
|------------|------------------------------------------|------------------|----------------------------------------------------------|
| Postgres   | `postgres:18` → 18.4                      | ✅               | `pg_dump --no-owner --no-privileges <db> \| gzip -9`     |
| Redis      | `redis:8` → 8.8.0                         | ✅               | `redis-cli -a <pw> BGSAVE` then copy `/data/dump.rdb`    |
| ClickHouse | `clickhouse/clickhouse-server:25.8` → 25.8.24.21 (LTS) | ✅   | `BACKUP TABLE <t> TO File('<t>.zip')` under `/var/lib/clickhouse/backups/` |

ClickHouse fits on the `e2-standard-2` VM with `limits.memory: 2Gi` plus a
`config.d` cap of `max_server_memory_usage: 1610612736` (1.5 GiB) — node sat at
~34% memory with 0 restarts.

## Apply (disposable namespace)

```bash
kubectl create namespace db-spike
kubectl apply -f cluster/examples/db-spike/postgres.yaml
kubectl apply -f cluster/examples/db-spike/redis.yaml
kubectl apply -f cluster/examples/db-spike/clickhouse.yaml
```

On this cluster, run these on the VM via `sudo k3s kubectl` (the workstation
cannot reach the k3s API directly — see the plan's Context section).

## Tear down

```bash
kubectl delete namespace db-spike
```

The `local-path` reclaim policy is `Delete`, so the per-PVC host directories
under `/var/lib/nagare/local-path` are reclaimed automatically.

> **Known cluster issue (input to EP-47):** in-pod GCS upload via the
> `GCE_METADATA_HOST=169.254.169.254` ADC pattern is currently broken — the
> metadata IP is routed into the `flannel.1` overlay and is unreachable from
> pods *and* the host. The backup *commands* above produce valid artifacts
> locally; the *upload* leg is EP-47's to fix (a node-route fix or a host-side
> upload step).
